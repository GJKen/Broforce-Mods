# 构建、部署与运行验证

本文汇总从源码到游戏内验证时容易混淆的环节。它是检查清单，不替代具体项目的构建脚本；某个角色仓库已有专用资源流水线时，以项目 README 和脚本为准。

## 1. 先确认实际构建入口

BroMaker 角色项目常见的构建方式有 MSBuild targets、命令行 `csc.exe` 和项目自带 PowerShell 脚本。这些方式的资源生成、编译引用、输出布局和部署行为可能不同。动手前先确认：

- 哪个脚本或工程是当前项目的正式入口。
- 编译器和目标框架分别是什么；目标框架本身不能确定编译器支持的 C# 语法。
- 游戏 `Managed`、UMM、BroMaker、RocketLib 和其他依赖 DLL 来自哪个安装或 profile。
- 生成资源的源稿位置、输出目录和是否会被构建覆盖。
- 部署目标是否与当前启动的 r2modman profile 一致。

本知识库的 [`templates/BuildBro.ps1`](templates/BuildBro.ps1) 是简单示例：它从唯一的 `.mod.json` 读取 `Assemblies`、编译对应 DLL，并递归复制 `_Mod` 内容。复杂角色应使用项目自己的构建入口，例如 [Aquabro](../CustomBro/Aquabro/README.md) 的资源构建说明。不要把模板的能力推断到其他构建系统上。

## 2. 配置路径与引用程序集

把 [`LocalBroforcePath.props.example`](templates/LocalBroforcePath.props.example) 复制成仅供本机使用的 props 文件，并按实际安装填写路径。不要提交包含个人目录、用户名或 profile 布局的配置。

先从目标游戏 `Managed` 目录确认游戏和 Unity 程序集。`Assembly-CSharp.dll`、Unity 模块、`UnityModManager.dll` 与 `BroMakerLib.dll` 是常见基础引用；Harmony、RocketLib、Newtonsoft.Json 及额外 Unity 模块只在代码或依赖需要时引用。Unity API 拆分到不同模块后，缺失类型时应查类型所在程序集，不要盲目复制某台机器的引用列表。模板可通过 `AdditionalReferencePaths` 添加分号分隔的模块 DLL。

编译通过只说明本次源文件可针对当前引用生成程序集，不说明目标游戏已加载正确版本，也不说明资源路径、网络行为或运行时逻辑正常。

## 3. 核对 mod 清单和输出路径

检查 `.mod.json` 中 `Assemblies` 的每个相对路径都对应实际生成的 DLL；`CustomBros` 和 `Abilities` 则应是有效的相对 JSON 路径或当前 BroMaker 支持的内联定义。大小写、子目录和程序集文件名都要与输出一致。

每次部署前确认：

1. 构建输出目录里有本次生成的程序集和预期资源。
2. 部署脚本保留子目录相对路径，角色 JSON 引用的贴图/音频确实在目标位置。
3. 目标 `BroMaker_Storage/<角色目录>/` 对应当前 UMM profile。
4. 游戏进程已经退出，再覆盖 DLL 和资源；暂停游戏不算退出。

构建和部署是两个步骤。使用 `-SkipDeploy` 或类似选项时，不要误以为游戏目录已更新；反过来，只复制 DLL 也可能漏掉 JSON 和资源。

## 4. JSON 字段值与初始化顺序

BroMaker 的阶段字典会对实际提供的键调用字段赋值逻辑；空字典不会仅凭“字段没写”就把所有字段统一清零。但最终值仍可能受 `HeroType` 预制体、Unity 序列化值、`Awake` / `Start` 及角色自身代码影响。

遇到数值与预期不同，按顺序确认：

1. 游戏加载的是哪个角色定义和哪个 DLL。
2. 字段名和字段类型是否匹配当前 BroMaker/角色类。
3. 字段在哪个阶段赋值，后续初始化是否又改写它。
4. 运行时角色实例上的最终值，而不是只看磁盘 JSON。

重要数值可以显式写入以固定角色设计，但不要把某次旧测试中的 `fireRate` 零值推广成“所有空字段都会清零”。字段参考见 [06 JSON 参数与变量参考](06-JSON参数与变量参考.md)。

## 5. 贴图与生成资源

贴图画布、帧尺寸、帧序和角色动画逻辑共同构成运行时约定。替换材质后检查 `SpriteSM` 的纹理重算、默认尺寸、lower-left 坐标和 UV 更新；只确认 PNG 文件存在不足以证明游戏读取了正确帧。

源稿、导出图集、遮罩及程序集应来自同一轮确认过的构建。不要直接编辑生成目录后期待下次构建保留，也不要让多个脚本分别产出互相不匹配的资源版本。对共享/缓存材质做单对象修改前，先确认材质所有权；需要独立效果时使用独立材质实例并管理其生命周期。

## 6. 分层验证并记录边界

按风险逐层确认，不要把不同证据混为一谈：

| 层级 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| 编译成功 | 源码针对当前引用生成 DLL | 游戏加载了新 DLL、资源有效或玩法正确 |
| 文件部署检查 | 文件位于预期 profile 和目录 | BroMaker 接受清单、角色成功实例化 |
| 启动日志与角色列表 | mod 被发现/加载，或角色可选 | 攻击、死亡清理、Boss 和联机行为正确 |
| 单项运行测试 | 指定场景下某条输入或效果正常 | 完整关卡、低频状态或不同 Boss 都覆盖 |
| 完整战斗/联机验证 | 实际覆盖到的场景与玩家模式 | 未测试的角色、阶段、平台或网络条件 |

运行时检查时确认当前游戏由目标 profile 启动，读取这次启动对应的 UMM 与 BroMaker 日志。若最新 `.log` 和 `.trace.log` 都是 0 字节，也要查看文件时间、目录和 UMM `Core/Log.txt`，再判断日志是否尚未写入或启动流程是否中断。

报告结果时记录游戏、BroMaker/RocketLib 版本，部署的构建时间或提交，以及实际测试场景。明确区分“捕获到伤害请求”和“目标实际扣血”，也区分“离线单项通过”和“完整关卡/远程联机通过”。未覆盖的路径保留为待验证，不根据相似外观或相似代码宣称通过。

# 角色贴图编辑与资源流水线

本文记录在需要逐帧保留特定原版动作时，如何用 Aseprite MCP 辅助像素级编辑。是否重绘骨架、沿用原帧、批量生成或自动导出，必须服从当前角色的美术需求；自动化导出、图集打包、遮罩生成和检查脚本都是合理的资源流水线工具。

---

## Aseprite MCP:配置与验证

### 装在哪

| 项 | 值 |
|---|---|
| MCP server 配置 | 配置在当前 MCP host 支持的位置 |
| 实现 | 由项目/用户环境提供的 Aseprite MCP server |
| Aseprite 本体 | Aseprite 可执行文件；不要求安装在固定路径 |

### 必须配 `ASEPRITE_PATH`

具体 server 通常通过环境变量或 `PATH` 定位 Aseprite。先检查所用 MCP server 的配置方式：

```python
cmd = [os.getenv('ASEPRITE_PATH', 'aseprite')] + args
```

Aseprite 不在 `PATH` 且执行文件路径未配置时，实际文件操作无法启动。路径以本机安装为准。

例如，在 MCP host 的 server 配置中传入环境变量：

```json
"env": { "ASEPRITE_PATH": "<Aseprite 可执行文件路径>" }
```

配置何时生效取决于 host；通常需要重启对应 MCP server 或 host。用会读写真实文件的操作验证，不要只依赖静态帮助工具。

### ⚠️ 验证陷阱:别被 `list_palette_presets` 骗了

有些工具只返回说明数据，并不调用 Aseprite。因此：

- 环境变量没配好时,它们**照样返回正常结果**;
- 拿它们做连通性测试 → 误判成"MCP 是好的"。

验证时调一个会访问真实文件的工具，或直接用 Aseprite CLI 执行小型探针：

```bash
export ASEPRITE_PATH="<Aseprite 可执行文件路径>"
"$ASEPRITE_PATH" --batch --script probe.lua        # probe.lua 里建 sprite 并 saveAs
```

`--batch` 模式下 Lua 里 `print()` 是唯一回传通道;**退出码为 0 不代表逻辑成功**,要 print 出中间结果。

## 画角色的正确流程(核心)
制作【角色名】的【动作名称】，对应原版【参考角色】身体图集【起止格号】，共【帧数】帧。

【当本任务要求逐帧沿用原版动作时：这是原动作逐像素换装】
我要保留参考角色的原版动作，把其外观替换为我的角色。
“参考原版”在本任务中明确表示：以每一帧原版像素为身体骨架底稿, 还要注意区分服饰像素, 因为有的服饰像素会超出身体外部, 会影响身体骨架底稿。
不要根据动作含义重新设计姿势，也不要重新画一套近似骨架。

【必须保留】
1. 每帧发型、面部、躯干、手臂、手掌、裤腿和脚的位置、大小、角度及轮廓。
2. 原版四肢长度、屈伸幅度、手脚接触点、遮挡关系及帧间位移。
3. 原版收身、旋转、展开的节奏，以及各帧不同的高度。
4. 原有皮肤像素原则上原位保留；需要调整肤色时，仅替换颜色。

【允许替换】
以【最新外观主稿路径】为准，替换头发、面部细节、衣服纹理、裤子和鞋靴的配色与材质。
例如：黑发改金发、军装改鳞甲、棕裤改绿裤。
外观替换尽量在原版部位轮廓内部完成，发型可根据自定义角色的发型在轮廓外部完成，不放大头、不加粗手臂、不拉长腿脚。

参考角色特有的头带、武器或装饰需要移除时：
- 飘在身体外的部分可以删除。
- 遮住身体的部分，应补回对应的头发、皮肤或衣服。
- 不能留下透明接缝、断臂或游离像素。
- 原版已有的手臂与身体间隙不要一律填平。

【工作方式】
1. 先阅读仓库规范和动作文档，核对实际取帧顺序、初始化、递减及播放时序。
2. 先查看原版对应帧，以及最新角色主稿。
3. 使用 Aseprite MCP 逐帧换装，不使用 Python 自动生成或改造角色像素。
4. 不用整图旋转、自动拼头、参数化骨架或其他动作帧代替本组原版动作。
5. 保留可编辑中文分层：裤靴、躯干、头发脸部、前侧手臂、后侧手臂；武器按本动作要求独立处理。
6. 空中动作保留原版位置变化，不强行对齐站姿脚底。
7. 已完成动作保持原样；用户维护的只读副本不可修改。

【验收必须提供】
- 每帧“原版 / 换装后”并排对照，标注源稿帧号与图集格号。
- 核对是否移动、增大或缩小了任何部位。
- 检查皮肤像素位置、原轮廓外新增像素、透明接缝、游离像素、半透明像素和裁切。
- 对必须改变轮廓的地方，逐项说明具体帧号、坐标和原因。
- 正常速度与慢速预览均从最终保存的源稿导出。

如果角色特征确实无法在原轮廓内表达，先指出具体冲突并展示局部对照，等待我选择后再扩大轮廓。

本次只制作【动作名称】，交付【源稿路径】及【预览和说明目录】。

## 和 Broforce 接轨

画完要进游戏时,导出尺寸和帧布局必须对(详见 [11 文档](11-导出官方贴图与资源包.md)):

| 贴图 | 尺寸 | 栅格 |
|---|---|---|
| 身体 | 1024×512 | 32 列 × 16 行 × 32×32 = 512 帧 |
| 枪 | 1024×64 | 32 列 × 2 行 × 32×32 |
| 头像 | 128×64 | 4 格 32×64 |
| 特技图标 | 16×16 | 单张 |

**帧号 = 行号 × 32 + 列号**,每个帧号播什么动作见 11 文档的对照表。

> 官方角色图可从当前导出结果 `Broforce_src/GameAssets/hero/` 中查找；数量随游戏版本和导出筛选变化。画之前先打开对应角色确认动作和帧布局。

## 未启用的动作格能否留空

**可以。只要运行时确定不会取到某个动作格,该格保持全透明即可,不需要补画,也不需要为了它删除动作代码。** 游戏按固定坐标从图集中取样,不检查该格是否有像素；取到透明格通常不会报错,只会让角色在那一帧不可见。

这里的“留空”仅指清空固定格子里的像素。必须保留图集画布尺寸、32×32 栅格和所有已有格号,不能删除格子后让后续动作前移,也不能自动紧密打包。角色代码和原版基类普遍使用 `SetLowerLeftPixel` 或等价公式直接计算坐标,一旦裁剪、重排或改变格号,后续动作会读到错误位置。

判断一个动作能否留空时,必须同时核对：

1. 角色自己的动画重写及硬编码格号。
2. `BetterAnimation` 和 `useNew*Frames` 等开关的最终值。
3. 击掌、死亡、翻滚、口袋特技、地形动作和能力强化等低频入口。
4. 其他 Mod 或事件是否会通过 `SetGestureAnimation` 等 API 主动触发该动作。

“平时没有见过”不能作为删除依据。例如 `BetterAnimation=true` 会启用 `hasNewAirFlexFrames`；获得 `FlexAirJump` 后,空中 Flex、前空翻、砸地和起身帧都会被取用。新版击掌也会读取完整的 17–22 格。透明留空这些格子不会阻止逻辑运行,只会在触发时缺画面。

如果动作当前明确由开关关闭,素材可以暂时留空。例如 Aquabro 明确设置 `useNewLadderClimbingFrames=false` 和 `useLadderClimbingTransition=false`,因此当前配置不会读取专用爬梯 160–173 和进出梯 192–197。以后重新开启开关时,必须同时恢复对应素材。

不要为了匹配空白贴图而把 `Animate...` 方法删除或改成空方法。动画方法往往还负责调用特技、释放物体、触发伤害以及清理状态。若一个可运行状态不准备单独绘制,应保留状态逻辑,只把显示帧重定向到一个已有姿势。

### TonyBrotana 对照结论

2026-09-18 的历史审计曾按 32×32 格比较 TonyBrotana 与当时的 Rambro 图集，发现部分格子为空但动画逻辑仍可触发。统计只对应当时的本地素材快照，未在本次重新测量；案例源码入口见 [14 文档](14-Gorzontrok三bro源码地图.md#tony-brotana主攻击混合弹射物)。

2026-10-14 补充源码入口：角色定义实际内联在 `TonyBrotana\_MOD\gz.tonybrotana.mod.json` 的 `CustomBros` 中，没有独立角色 JSON；主类、火箭循环与版本信息见 [14 文档](14-Gorzontrok三bro源码地图.md#tony-brotana主攻击混合弹射物)。本次整理未重新统计动作格，上述数字保留原审计日期。

Tony 确实把大量非 Flex 手势素材留空,但它也缺少新版击掌末帧及 `FlexAirJump` 可触发的空中动作。因此它只能证明“图集允许透明格”,不能证明它省略的每一格都不会运行,也不能直接作为其他角色的安全删帧表。

清空像素只会略微减小 PNG 的压缩后文件大小。只要画布仍为相同尺寸,运行时纹理占用基本不变；不要为了节省显存而冒险裁剪或重排图集。

## 这套工具还有什么用

除了画新图,批量处理类活很适合交给它(比手写脚本省事):

- 把某角色整版图逐帧过一遍,生成带帧号标注的接触表
- `render_onion_skin` 查动作帧之间连不连贯
- `compare_frames` 比两帧差异,确认改动真的生效
- `color_stats` 查用了多少种颜色(像素画配色纪律)
- `export_spritesheet` / `export_frame` 导出与放大自查
- `run_lua_script` 是兜底出口:上面没覆盖的操作,直接写 Lua

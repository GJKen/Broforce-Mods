## 原版调用链证据

### 1. 原生死亡 RPC 可能跳过完整死亡流程

`Unit.Death` 向 `PID.TargetOthers` 发送冲量和死亡位置，然后写入 `actionState=Dead`。接收端 `Unit.DeathRPC` 只有在本地 `actionState != Dead` 时才会调用虚拟 `Death`。

这意味着只要接收端通过其它状态路径先进入 `Dead`，后到的死亡 RPC 就会被整个跳过。本文尚未用调用时序日志证明本次官方地图样本一定经过了这条竞态，因此当前将它列为源码确认的缺陷窗口，而不是本次现场已经闭环的唯一根因。

### 2. 接收端死亡上下文为空

`Unit.DeathRPC` 调用 `Death(xI, yI, null)`。`Mook.Death` 会继续进入 `TestVanDammeAnim.Death`，而后者在完整的空值保护之前读取 `damage.damageSender`。因此远端原版死亡调用存在缺失伤害上下文和中途退出的风险，也无法可靠统一 `DamageType`、最终 health、击杀归属相关分支和死亡物理参数。

### 3. 死亡开始时立即关闭同步

`TestVanDammeAnim.Death` 在死亡逻辑前段调用 `SetSyncingInternal(false)`。之后尸体冲量、碰撞和落地由各端独立模拟；本次样本中双方均死亡但 Y 坐标分别为 `253` 和 `248`，与这种模型一致。

### 4. 尸体停用也由各端自行判定

`DisableWhenOffCamera` 根据本地 `IsOnGround()`、可见范围和 `PolymorphicAI.Syncronize` 决定何时停用单位。尸体物理一旦分叉，各端可能在不同位置、不同帧停用，进一步把短暂误差固化成最终位置差、楼层差或一端可见而另一端不可见。

### 5. NID 和统一 RPC 通道可以复用

原版 `Registry.GetNID`、`Registry.GetObject(NID)` 和 `TypeSerializer` 已支持以 NID 定位、序列化网络对象。FRP Direct 会转送原生游戏 RPC 字节，并由房主中继广播，所以实体同步层无需添加 FRP 专属控制协议。

## 修复原则

1. 房主是普通敌人死亡与尸体终态的唯一权威发布者。
2. Steam 和 FRP 共用同一个 RPC 与接收处理器。
3. 官方与 Workshop 地图共用同一个在线会话判断，不依赖 `EnableOnlineWorkshopInjection` 或 `IsWorkshopOnlineSession()`。
4. 使用 NID 作为第一阶段唯一实体键；`NID.NoID` 只记录诊断，不用类型加坐标猜实体。
5. 死亡事件与尸体终态分开：前者保证完整死亡链，后者保证物理模拟最终收敛。
6. 所有接收都必须幂等；重复、乱序或晚到 RPC 不得重复计数、掉落、音效或死亡。
7. 不用 12 Hz 持续纠偏尸体。只发布一次稳定终态，避免带宽浪费和尸体抖动。
8. 本机直接应用，远端使用 `PID.TargetOthers`；不依赖 `TargetAll` 是否在不同网络层可靠自回环。

## 分阶段方案

### 已完成实现：死亡事件与尸体终态同步

新增独立文件 `HarmonyDiagnostics.EntityFinalState.cs`，并接入项目编译项、Harmony 初始化和场景/离房清理。

实现要点：

- 房主在普通 Mook 首次完成死亡后按 `NID + deathSequence` 广播死亡位置、冲量、DamageType 和 health。
- 远端按 NID 查找实体，使用非空 `DamageObject` 补全死亡链；原生 `DeathRPC` 也使用非空上下文回退，避免空伤害上下文导致中途退出。
- 重复、乱序和找不到 Registry 对象的消息按序列幂等处理并短暂排队。
- 房主在尸体落地稳定、即将停用或超时后只广播一次尸体终态；远端设置权威坐标、health 并归零速度。
- 远端尸体在等待终态期间最多延迟停用 2 秒，超时后恢复原版停用。

需要记录的事件：

- `ENTITY_FINAL death-enter`：NID、类型、是否房主、`IsMine`、health、`actionState`、`hasDied`、坐标、冲量和 `DamageType`。
- `ENTITY_FINAL death-rpc-enter`：接收时相同状态，确认 RPC 是否因已经 `Dead` 而被原版跳过。
- `ENTITY_FINAL death-exit`：死亡链完成后的 health、`actionState`、`hasDied`、碰撞器和同步状态。
- `ENTITY_FINAL corpse-disable`：停用前坐标、速度、`IsOnGround()` 和是否已有权威终态。

运行时验收仍需在双方完全退出并重启游戏后进行：至少在官方地图和一张 Workshop 地图各击杀数个普通 Mook，确认房主一定能观察到每次死亡，并确认双方同一 Mook 的 NID 一致。若第三方动态敌人出现 `NID.NoID` 或 NID 不一致，应另开实体登记问题，不能在本方案中用坐标猜测兜底。

### 第二阶段：同步权威死亡事件

房主首次完成某个网络登记 Mook 的死亡流程时，发送一次权威死亡 RPC：

```text
NID + deathSequence + deathPosition + xI/yI + DamageType + terminalHealth
```

接收端按 NID 查找自己的 Mook：

- 尚未完成死亡链时，先采用权威位置并构造非空 `DamageObject`，再进入一次原版虚拟死亡流程。
- 已经完整死亡时，不重复执行统计、掉落、音效和死亡动画，只登记该序列已经消费，并等待尸体终态。
- 只处于 `actionState=Dead`、但 `hasDied`、碰撞器或关键清理状态不完整时，执行专门的补全路径；不能直接依赖原版 `DeathRPC` 的 `actionState != Dead` 判断。
- RPC 重复到达时按 `NID + deathSequence` 幂等忽略。
- 找不到 NID 时记录 `death-miss`，允许短时间排队等待 Registry 登记；超时后放弃，不匹配附近同类型实体。

`terminalHealth` 用于统一本次样本中的 `0` 与 `-9`，但不得再次计算伤害或触发受伤副作用。

### 第三阶段：提交一次尸体终态

房主在死亡 Mook 满足以下任一条件时发布一次尸体终态：

- 已落地且速度连续若干采样低于阈值。
- `DisableWhenOffCamera.Disable` 即将停用该尸体。
- 达到受控超时，避免特殊尸体永久等待。

终态数据至少包含：

```text
NID + deathSequence + finalPosition + finalHealth + facing + zeroVelocity
```

应用规则：

- 房主本地直接提交，然后向 `PID.TargetOthers` 广播。
- 远端设置权威坐标和 health，归零尸体速度，并立即刷新 Transform。
- 远端在等待权威终态期间，窄范围延迟该 Mook 的 `DisableWhenOffCamera.Disable`；收到终态或超时后恢复原版停用。
- 终态只能应用于已经死亡的同 NID Mook，不能把活体强制变成尸体。若终态先于死亡事件到达，短暂排队并等待对应 `deathSequence`。
- 不对尸体开启持续 `Syncronize`，避免状态包覆盖逐帧物理造成抖动。

### 第四阶段：晚加入状态重放

房主按场景缓存已经提交的 `NID -> deathSequence + death event + corpse terminal`。加入方完成 Registry/场景同步后请求一次死亡实体快照：

- 已死亡但仍存在的实体重放死亡完成状态和尸体终态。
- 已经由原版销毁且 Registry 不再存在的对象按原版销毁同步处理，不在本方案中重建尸体。
- 缓存在切关、离房、主机迁移和 Mod 停用时清空，禁止跨场景复用 NID。

晚加入重放必须使用同一原生 RPC 通道，因此 Steam 和 FRP 不增加分支。

## 实现边界建议

建议新增与 `Workshop` 解耦的会话判断，例如 `IsOnlineEntityFinalStateSession()`：

- 要求当前确实在线、网络 PID/Registry 已就绪。
- 接受 `SteamLayer` 和 `FrpDirectLayer`。
- 不要求 Workshop 注入开关开启。
- 离线、本地测试和其它未知网络层默认不启用。

第一轮只接受满足以下条件的目标：

- `Mook` / `PolymorphicAI` 普通敌人。
- `Registry.GetNID(mook) != NID.NoID`。
- 非 Hero、非载具、非 Boss、非已销毁对象。

死亡补全逻辑与终态提交逻辑应分别封装，避免一个 Harmony 前缀同时承担伤害、统计、物理和停用控制。

每个组合至少验证：

1. 普通枪击死亡。
2. 爆炸冲量死亡。
3. 尸体从平台或高处落下。
4. 尸体离开镜头后被 `DisableWhenOffCamera` 停用。
5. 同一关卡中途加入。
6. 连续击杀多个相同类型 Mook。
7. 200ms 左右延迟或可复现乱序条件。

通过标准：

- 双方对同一 NID 的 `actionState`、`hasDied`、health 和启用/碰撞状态一致。
- 尸体终态坐标一致；建议坐标误差不超过 `0.5`，落在同一平台或楼层。
- `death-owner`、每个远端的 `death-apply`、`corpse-owner-terminal` 和 `corpse-terminal-apply` 对同一 `NID + deathSequence` 各出现一次。
- 不出现重复击杀统计、重复掉落、重复音效或重复死亡动画。
- 敌人总数和死亡数一致，且不能仅以总数一致代替逐 NID 验证。
- Steam 和 FRP 使用相同日志事件与处理分支。
- 官方地图在 Workshop 注入关闭时仍启用本修复；离线模式保持原版行为。

## 回归风险与停止条件

- 若房主并不能可靠观察所有客户端造成的敌人死亡，应先修正伤害/死亡权威来源，不能继续叠加尸体终态广播。
- 若第三方地图的普通敌人没有稳定 NID，应把网络登记作为独立前置问题。
- 若完整死亡补全造成重复钱币或击杀统计，立即停止扩大测试，先收紧幂等边界。
- 若 `DisableWhenOffCamera` 延迟导致尸体永久占用，应保留超时恢复原版停用，并记录超时 NID。
- 玩家、载具或 Boss 一旦进入补丁范围，视为范围保护失败，必须先修正过滤条件。

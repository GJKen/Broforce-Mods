# 联机房主敌人逐帧更新负载

## 状态

| 项目 | 状态 |
| --- | --- |
| 用户现象 | 联机时低帧；本地自定义战役在 `vSyncCount=0` 时保持高帧 |
| Mod 因果 | 瓶颈在原版 Steam 身份查询；用户后续授权将有效修复整合到 `CustomMapMultiplayer` |
| 原生更新热点 | MCP 计时：`Mook.Update` 约 `14.7 ms/帧`，`DisableWhenOffCamera.Update` 约 `3.1 ms/帧`；Steam 网络层约 `0.28 ms/帧` |
| 场景实体 | 约 199 个敌人记录、16 个活动敌人 AI、218 个镜头外检查组件 |
| 修复 | BroforceBugFix 0.4.0 裁剪实验未解决问题、不迁入；0.5.0 身份查询缓存精简整合到 CustomMapMultiplayer 0.5.1 |
| 验收 | 用户已先后确认房主稳定高帧、加入方联机帧率正常；详情见身份查询记录 |

计时数据用于确定修复方向，不足以单独证明所有地图低帧都由 Mook 更新导致。之前有一个 10 秒样本在游戏未聚焦时取得，不作为性能验收。

## 0.5.0 接续结果

后续定位发现，`Mook.Update` 及镜头外检查中的多次所有权判断会反复调用 `SteamLayer.IsHost`，每次都通过 Steam API 查询身份。新修复缓存同帧、同网络层和同房间的查询结果，并在 Steam 回调及成员/数据事件时失效。180 帧开关对照中，原版 getter 从约 249 次/帧降至约 1 次/帧，累计耗时从 10.36 降至 0.11 ms/帧，活动 Mook 数保持 14。详见 [Steam 房主身份重复查询](ISSUES-2026-11-11-Steam房主身份重复查询.md)。

用户随后实测确认帧率恢复稳定高帧、没有问题。本次仅迁入身份查询缓存；以下 0.4.0 记录及其失败结论作为历史保留，原“不得修改 CustomMapMultiplayer”是当时边界，已由用户后续整合要求更新。

## 用户复测

2026-11-11，用户安装并进入游戏测试后报告：联机帧率仍约 40 FPS，没有达到预期的 100 多帧。该结果是用户提供的实测反馈，不是本次 MCP 独立测量。0.4.0 的房主 Mook 镜头外裁剪优化效果不足，不能据此认定 Mook 是唯一根因；需要继续查明联机与本地高帧之间的实际负载差异，并修复主要瓶颈。

用户此前确认本地自定义战役在 `vSyncCount=0` 时仍保持高帧，也说明无需把垂直同步或固定同一位置作为前提。不得将问题归因于 `CustomMapMultiplayer`，也不得修改该插件。

## 当前运行时检查

2026-11-11 通过 Unity Inspector MCP 只读检查时，当前场景为 `Test Evan2`，战役 `Contra Predator II`，游戏状态只报告 1 名玩家。网络层为 `SteamLayer`，`Connect.IsOffline=false`、`Connect.IsHost=true`；这说明当前进程处于主机网络层，但 MCP 没有证明第二名玩家或双端低帧现场存在，不能当作用户所报联机卡顿的复现。

当前关卡 MCP 列出 200 个敌人（196 个存活），查询到 214 个 `Mook` GameObject 和 217 个带 `PolymorphicAI` 的 GameObject。查询只报告 GameObject 激活状态，不等于相应脚本组件都在运行。抽查的一个 `MookTrooper` 上，`DisableWhenOffCamera` 缓冲为 `96 x 80`，`MookTrooperAI` 与 Mook 均启用，AI 状态为 `Idle`，`Syncronize=false`；`MapController.currentActiveMooksInScene` 当时为 3。该快照证明 0.4.0 的范围调整在当前对象上生效，不证明它解决了用户的双端低帧。

同一时刻读到 `Time.deltaTime=16.6 ms`、`Time.smoothDeltaTime=20.3 ms`、`Application.targetFrameRate=120`、`QualitySettings.vSyncCount=1`。这是单帧/平滑帧间隔快照，不是稳定帧率测试；当前现场没有复现或验证约 40 FPS。此前用户报告 `vSyncCount=0` 时本地自定义战役仍高帧，该结果仍按用户反馈记录。

源码发现一个需要优先评估的剩余负载：原版 `DisableWhenOffCamera.Update` 每帧先调用 `RunForceExtents()`，之后才按 `0.2s` 间隔进行可见性判断。0.4.0 通过关闭远处 Mook 的 `Unit` 和 `PolymorphicAI` 来减少其主体更新，但 `DisableWhenOffCamera` 自身仍启用。此前约 `3.1 ms/帧` 的该方法计时因此仍是值得核实的候选热点，而不是已证明的完整根因。`NetworkObject.LateUpdate` 也需按同步对象状态评估；源码中 `RunSync()` 会在 `Syncronize=false` 或无状态时快速返回，抽查对象为 `Syncronize=false`。不得从 GameObject 总数直接推断每帧实际工作量。

## 原版调用链

`Mook.Update` 调用 `TestVanDammeAnim.Update` 和 `Mook` 自身的状态、物理及受伤逻辑。房主负责本地 AI 所属敌人的模拟。原版 `DisableWhenOffCamera` 每 `0.2s` 检查对象是否仍应启用；对象默认保留水平 `160`、垂直 `128` 的镜头外缓冲。多人镜头覆盖的玩家区域扩大时，更多 Mook 可能同时留在更新范围内。

上述解释与运行计时和原版源码相符，但“多人镜头扩大导致全部差异”仍是待验证机制，不作确定性根因声明。

## 修复行为

- 新增独立开关 `EnableMultiplayerMookCullingFix`，默认开启。
- 仅在线房主的 Mook 使用水平 `96`、垂直 `80` 的镜头外缓冲上限；地图原始值更小则保留原值。
- 离线游戏和加入方保留地图设置。
- `DisableWhenOffCamera` 原生判断仍决定是否停用；受脚本控制、镜头内及原版判定必须启用的单位不受影响。
- 关闭该设置、插件主开关或卸载插件时恢复对象的原始缓冲。
- 不改网络协议、RPC、AI 决策、伤害或单位生成。

预期收益来自减少房主逐帧更新的远离视野 Mook 数量。代价是玩家离开后，远处敌人更早暂停模拟，靠近时重新启用；用户复测仍约 40 FPS，当前优化没有带来足够的帧率收益。

## 验收

1. 联机房主不再停留在约 40 FPS，帧率明显改善并接近用户本机本地自定义战役的 100+ FPS 水平；以用户实际体验验收，不把单纯减少活动 Mook 当作修复通过。
2. 加入方帧率和行为没有回退。
3. 离线自定义战役保持原有高帧及敌人行为。
4. 受脚本控制的敌人、跳跃/坠落中的敌人和未落地尸体仍持续运行。
5. 关闭独立设置后缓冲恢复原值，重进关卡后不残留状态。

以上为 0.4.0 裁剪实验的验收：当时第 1 项未通过，其余项目未由该次复测确认；该实验不再作为当前实现。后续身份查询缓存的用户高帧验收见本文开头及关联记录。

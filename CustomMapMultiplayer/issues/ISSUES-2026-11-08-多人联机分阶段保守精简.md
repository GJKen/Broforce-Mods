# 多人联机代码分阶段保守精简

## 目标与约定

用户希望精简多人联机代码，同时保持现有功能、机制和执行时序。精简量不设目标；优先删除有引用证据支持的无效代码、只写不读字段和纯转发包装，不为减少行数改写有效联机逻辑。

- 每阶段单独限定范围，先核实直接调用、反射字符串及测试脚本引用，再修改。
- 保留网络条件、Harmony 注册顺序、状态清理顺序、实际适配器及其异常处理。
- 每阶段完成标准构建，由执行会话自行使用 Unity Inspector MCP 验证，并记录实际结果及未覆盖项；脚本提交不等于验证通过。
- 验证完成后创建独立本地提交，便于比较和回退；本任务暂不推送。
- 全部阶段结束后，可以把本任务的多个本地提交压缩为一个提交。压缩前核对范围、保留恢复点，不纳入其它项目或用户修改；未推送的阶段提交压缩不涉及远端历史重写。该约定已于 2026-11-09 执行，范围与恢复点见文末。
- 部署前确认游戏退出；实测结束关闭两端游戏并清理临时对象。

## 新问题：退出游戏后首次 FRP Direct 房间角色不可见

用户报告：退出游戏后首次创建 FRP Direct 房间，进入后角色不可见，但有角色头像 UI。用户确认的阶段六步骤 1-3 正常；本问题单独跟踪，不据此推定为阶段六精简回归。

前次通过本机和 remote Unity Inspector MCP 检查时，两端均在 `Test Evan2`、`playerCount=2`，本机为 FRP Host、内网为 FRP Client，双方都有本地角色；那次读取没有重现空角色。本机和内网的会话日志都报告上述相同 Build hash。

对应日志还记录过另一个独立现象：客户端在 Host 房间仍处于 `newJoin`/`loading` 时开始 Workshop 地图加载。客户端本地 `HeroController.SpawnJoinedPlayers()` 于 `+5.440s` 被观察到，此时等待状态仍是 `readiness=not-ready`；它随即首次请求本地 `player=0; controller=0`。Host 到 `+34.164s` 才发布 Workshop `ready=1`，并于 `+34.230s` 执行本地 `Player.Start`、占用槽位 0。Host 在 `+65.482s` 收到客户端的 `RequestJoinGame` 后将其分配为 `player=1`。客户端在首次请求约 45 秒超时后重试槽位 1，于 `+51.850s` 确认本地 `Player.Start`，`+52.146s` 进入 `Player.SpawnHero`。日志证实该客户端槽位曾有约 52 秒没有 `character`，随后自动重试生成；这是加入端延迟生成，不能解释本次已确认的 Host 角色对象存在但不可见。

本次本机 MCP 现场复核：本机在 `Test Evan2`、`Connect.IsHost=True`、`Connect.IsOffline=False`、连接层为 `FrpDirectLayer`，内网端已在 `MainMenu`。场景截图显示左下角色头像和 1 条生命，但地图中没有角色。`HeroController.players[0]` 与玩家对象均存在且 active，`Player.character` 为 `Rambo(Clone) [local]`；角色 `health=1`、`IsAlive=True`、`actionState=Idle`、`HidingPlayer=False`、出生位置为 `(64,80,0.0466)`，但角色根 GameObject 的 `activeSelf=False`、`activeInHierarchy=False`。角色组件和 Renderer 均启用，角色 prefab 本身 `activeSelf=True`；运行时 `UpdateHasRunAtleastOnce=False`。这确认问题是已分配角色对象被停用，不是头像 UI 对应槽位为空。

本机进程内 `BroMakerLib.Loggers.BMLogger` 记录 `[06:28:49] [Warning] No network-compatible BroMaker character is available; keeping the vanilla spawn.`，时间与 Host trace 中 `Player.SpawnHero(Rambro)` 及 `InstantiateHero` 的 `+35.02s` 相符。BroMaker 的 `Player_InstantiateHero_Patch` 在 `LoadHero.willReplaceBro[playerNum]` 为 true 时先对原生角色调用 `gameObject.SetActive(false)`；随后 `Player_SpawnHero_Patch.Postfix` 遇到 `choice == null` 会记录上述警告、清理替换标志并返回，却没有重新激活原生角色。于是 `Player.character` 仍指向有生命值的 Rambo 对象，头像 UI 正常，但角色根对象一直 inactive。当前运行时替换标志已归零，BroMaker 自动选择开启且当前网络可用角色数为 10；日志没有记录为何当次选择返回 null，具体选择失败条件仍未定位。

因此当前已确认的直接根因位于 BroMaker 的自定义角色替换失败回退：回退文字称保留原角色，实际没有恢复原生角色 GameObject。上一段客户端晚加入约 52 秒的记录是独立问题，不是本次 Host 画面无角色的解释。用户要求先在 BroMaker 项目 issues 建档、日后再处理；修复已暂缓，当前源码未保留未构建的修复改动。

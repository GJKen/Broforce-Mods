## 测试依据

本记录根据 `test007` 以及前面的 `test001`、`test002`、`test003`、`test004`、`test006` 的双端日志整理：

- `SteamLayer_CreateMatch` 会话的实际网络角色是 host。
- `SteamLayer_JoinLobby` 会话的实际网络角色是 client。
- 日志文件名中的 `Diagnostic label` 不是实际网络角色，判断角色必须看 `SESSION_BEGIN` 中的 `networkRole`。
- 本机文件虽然标记为 client，三轮实际都是 host；内网端文件虽然标记为 host，实际都是 client。

## test001-test003 复测结论

三轮测试都出现相同结果：进入 Workshop 地图后只能看到 host，client 按攻击键无法生成角色。因此问题二和问题三本轮无法复测。

双端日志确认：

1. client 会反复调用 `HeroController.AddLocalPlayer`。
2. host 能反复收到 client 的 `HeroController.RequestJoinGame(controllerNum=0)`。
3. host 始终没有执行远程玩家的 `HeroController.AddPlayer(playerNum=1, ...)`。
4. client 因此不会进入请求英雄类型和生成本地角色的阶段。

重新检查游戏原生 `HeroController.RequestJoinGame` 指令后确认：它会在 `LevelFinished=true` 时退出，也会在控制器注册检查返回 `true` 时退出。之前的日志把控制器检查描述成“已允许”，但补丁实际返回了 `true`，恰好触发原生提前退出，所以不会执行 `AddPlayer`。

已修正：

- Workshop host 在晚加入阶段将关卡结束保护条件改为不退出。
- Workshop host 在晚加入阶段让控制器检查返回 `false`，使原生方法继续执行 `AddPlayer`、PID 写入、玩家状态同步和数据请求。
- 普通线上关卡仍保留游戏原生判断。

`test004` 第二轮的 host 日志记录了：

针对 `test004` 已加入以下修正和诊断：

- 暂存的出生位置改为调用原生 `Player.SetSpawnPositon`，同时保留原始 `SpawnType` 和空投标记，确保 `spawnPositionHasBeenSet` 一并更新。
- host 在晚加入请求进入原生处理前记录 `GetNextUnusedPlayerNumber()` 和四个槽位的即时状态；如果发现 `playersPlaying=true` 但 `Player` 对象为空，则清理该明确失效槽位后再让原生请求分配。
- host 成功登记晚加入玩家后，延迟重发本机玩家已经确认过的原始出生坐标，给 client 的新 `Player` 对象留出创建时间。

## 问题一：进入地图后角色初始位置不一致

现象是角色第一次显示的位置不同，移动后才跳到正确位置。

`test001`、`test002`、`test003` 已记录到 host 调用 `Player.SetSpawnPositon(... pos=(64,224,5))`，但三轮 client 日志都没有收到对应的 `SetSpawnPositon`，只收到远程角色的 `SetPlayerCharacter`。这说明出生位置 RPC 在 client 的玩家对象准备好之前丢失了；角色 transform 虽然随网络对象到达，但内部坐标和出生状态没有经过原生初始化，直到移动同步时才被纠正。

当前 DLL 已处理，尚待下一轮双端复测：

1. 追踪 `Player.SetSpawnPositon`，保存本机角色原本收到的 `SpawnType`、空投标记和坐标。
2. 如果出生坐标先到、角色对象还不存在，则暂存坐标；角色对象创建后通过原生 `Player.SetSpawnPositon` 在本地补应用该原始坐标。
3. 不再在角色绑定后调用 `WorkOutSpawnPosition`。该方法会根据已经变为 `false` 的 `firstDeployment` 重新选择出生场景，错误地把首次出生改成中途空投。
4. 角色绑定或晚加入玩家登记完成后，本机只向其它客户端重发已保存的原始出生参数，不重新计算坐标。

## 问题二：client 闲置后角色被删除，再加入时变成死亡状态

日志中的关键顺序为：

```text
HeroController.DropoutRPC(playerNum=1)
HeroController.SetPlayerName(index=1, pName="")
HeroController.AddPlayer(playerNum=1)
Player.Start(... lives=0 ...)
```

`DropoutRPC` 会把本地玩家标记为本轮已经退出。client 再按攻击键重新加入时，游戏原生 `Player.Start` 会把生命数保留为 0，所以角色虽然重新加入，实际处于死亡状态。

已处理：

1. 记录本地 Workshop 玩家发生掉线式删除。
2. 同一个本地槽位重新加入时清除错误的“本轮已退出”状态。
3. 如果生命数仍为 0，则恢复为 1。
4. 如果角色没有生成，则重新请求英雄并生成角色。

## 问题三：client 底部持续显示“按开枪键加入游戏”

这是问题二的同一条状态链。`DropoutRPC` 清空玩家名称并将 `playersPlaying` 设为 false，游戏因此显示加入提示；host 自己的玩家没有经过这条路径，所以没有提示。

问题二的修复会让 client 重新加入后恢复为正常游戏玩家。新增的日志也会记录恢复过程，便于确认提示是否已经消失。

`test001`、`test002`、`test003` 中 client 从未成功生成角色，所以这两个问题尚未完成复测，不能根据本轮结果判断已经消失。

## 问题三最终验证

旧记录中“只影响 client”是当时的现象，不适用于当前实现。源码确认“按开枪键加入游戏”是 `HeroController.Update` 在本机没有可用玩家槽位时显示的通用 `LevelTitle` 横幅，并非 Lobby 专用提示。

最终修复在 `LevelTitle.ShowText` 前置阶段按本地化键 `LOC_HUD_PRESSTOJOIN` 的实际文本精确匹配。命中后同时阻止新的显示调用并隐藏已激活的横幅对象。处理范围仅限启用 Workshop 注入的线上会话，覆盖房主和加入方；不改变攻击键输入、`AddLocalPlayer`、`RequestJoinGame`、Lobby 或地图加载。

后续双端人工测试已确认：房主和加入方都成功屏蔽该横幅，攻击键加入功能仍可用。命中时日志会记录 `Suppressed the in-game Press To Join banner for the Workshop client.`；日志中的 `client` 是历史名称，当前实际覆盖双方。

## test006 新发现

本轮虽然没有修改会话编号，但日志中实际形成了三组独立会话。按 `SESSION_BEGIN.networkRole` 配对如下：

- 本机 `191115` 对内网 `191522`：host / client。
- 本机 `191344` 对内网 `191741`：host / client。
- 本机 `191911` 对内网 `192324`：host / client。

本轮重点结果：

1. 三组日志都出现了 client 同一控制器连续加入多个本地槽位的路径。最明确的一次在内网 `192324`：同一时间连续调用 `AddLocalPlayer(playernum=1/2/3, controllerID=0)`，随后 host 收到三个 `AddPlayer(playerNum=1/2/3, playerPID=IsMine=True)`。这直接解释了加入方出现三个角色并提示“游戏已满员，你在观战”。
2. 已有的“同一帧去重”不足以覆盖原生 `MonitorPlayerDropin` 的连续调用，且前一版只在 client 侧拦截。当前修复改为：Workshop 联机 host/client 两端都对同一控制器检查活动槽位并使用短暂请求锁；掉线时释放该控制器锁，允许正常重新加入。
3. 三组日志仍出现 `Player.Start(... lives=0 ...)`，并且在重复槽位场景中一次恢复了多个本地槽位。该现象是“三角色”问题的连带结果；先阻止重复槽位后，再验证单个 client 角色的闲置重加入，避免把旧的异常槽位误当成正常结果。
4. 位置问题的时序更清楚了：远端角色先以 `(0,0,0)` 或已经下落的位置完成绑定，之后收到的 `SetSpawnPositon` 只更新出生状态，首次显示位置没有统一。现已增加每个远端角色对象只执行一次的首次位置校正；晚加入时改用房主当前角色位置，避免把早期缓存的出生点重新发送给已经在地图中移动的房主角色。
5. 双端每次进入 `Test Evan2` 仍记录 `GeneratePole.Awake` 引发的 `NullReferenceException`。它是地图对象初始化错误，可能影响杆子和碰撞体状态；本轮修复先隔离联机角色同步问题，复测时仍必须单独记录该错误是否继续出现。

本轮日志没有独立的游戏 `error.log` 可供比对；已检查可取得的双端诊断 `.log`、`.trace.log` 以及 UMM `Core\Log.txt`。

## test007 复盘

本轮使用相同的 `test007` 会话 ID，实际形成两组双端会话。文件名中的 `role` 仍然只是诊断标签，实际角色以 `networkRole` 为准：

- 本机 `195247`（实际 host）与内网 `195716`（实际 client）。
- 本机 `195505`（实际 host）与内网 `200221`（实际 client）。

两端的 UMM `Core\Log.txt` 均确认 `SUCCESSFUL LOADED 1/1 MODS`，没有发现独立的游戏 `error.log`。内网端日志来自其本机的 `Application.persistentDataPath`，不是 DLL 部署共享目录。

本轮确认了以下问题：

1. 第一组会话中，host 先创建本地玩家，随后同一个 client 控制器的 `AddLocalPlayer` 路径在 host 上同时留下了远程槽位和额外的本地槽位。双端随后都能看到重复角色；host 端原有拦截没有生效，因为它只限制 client。
2. 第二组会话中，client 本地槽位掉线后恢复成功，但 host 本地槽位也出现了 `DropoutRPC`，重新加入时以 `Player.Start(... lives=0 ...)` 启动。原因是掉线记录和生命恢复逻辑仍然只对 client 开启。
3. 两组会话都出现 `GeneratePole.Awake -> Map.PlaceDoodad -> Map.LoadArea` 的 `NullReferenceException`。角色出生时先收到绳索上的固定出生点，之后又收到已经因物理下落产生的 `DropInDuringGame` 坐标。两端初始物理状态不同，直到移动同步才收敛；这与重复槽位问题相互叠加。
4. 本轮没有直接的 projectile 碰撞追踪，因此“子弹命中角色后反弹”的观察暂时只能作为位置、角色槽位和碰撞体状态不同步的伴随现象，不能单凭现有日志断定具体碰撞代码。

本轮之后的修复：

- `DropoutRPC` 记录、`Player.Start` 生命恢复和本轮退出状态恢复同时适用于实际 host 与实际 client，但仍只处理 `PID.IsMine=true` 的本地槽位。
- 同一控制器的 `AddLocalPlayer` 在 host/client 两端都检查活动玩家槽位，并增加短暂请求锁；掉线时释放该控制器锁，允许正常重新加入。
- 角色绑定后的出生广播改为等待物理状态稳定后发送当前权威坐标，并保留原始出生类型；不再把固定的绳索坐标再次覆盖到已经下落的角色上。

## test008 复盘与本轮修复

本轮按实际网络角色配对为：

- 本机 `202908`（实际 host）与内网 `203319`（实际 client）。
- 本机 `203411`（实际 host）与内网 `203816`（实际 client）。

两端 UMM `Core\Log.txt` 均为 `SUCCESSFUL LOADED 1/1 MODS`，未取得独立游戏 `error.log`。

第一组“双方同时进入地图”确认了重复加入方角色的完整调用链：client 在进入地图前已经有本地 `playerNum=1`，但晚加入分支又调用了 `AddLocalPlayer(-1, 1)`，原生分配出第二个本地槽位 `playerNum=2`。随后 `SpawnJoinedPlayers` 发现两个 `PIDS.IsMine=true` 的空槽位，连续广播：

```text
AddPlayer(playerNum=1, controllerNum=0, playerPID=IsMine=True)
AddPlayer(playerNum=2, controllerNum=1, playerPID=IsMine=True)
```

这就是加入方生成两个角色的直接原因。原有去重只按控制器号工作，并且只在 Workshop 场景状态已经确认后才启用；本轮两个请求的控制器号不同，且发生在场景状态稳定之前，因此未能阻止。

第二组“host 先进入地图、client 后加入”只有一个 client 本地角色，位置会自行恢复，host 闲置后重新加入也正常。该流程当前较好，本轮不改动其原生 `RequestJoinGame` 放行路径。

本轮修复：

1. 只要已创建线上会话、启用了有效 Workshop 注入配置，`AddLocalPlayer` 去重就开始生效，不再等待 Workshop 场景状态识别完成。
2. 每台机器同一时间只允许一个未完成的本地加入请求；已有本地槽位时禁止再申请任何控制器号的额外槽位。明确发生本地 `DropoutRPC` 后才释放该保护，保留正常重入。
3. 晚加入检测到已有本地槽位时复用该槽位，不再额外调用 `AddLocalPlayer(-1, 1)`。
4. `SpawnJoinedPlayers` 开始广播前，移除额外的本地空槽位，保留编号最小的合法本地槽位，避免已经形成的重复预留槽被广播为多个加入方角色。

## test011 晚加入后立即按攻击键观测与修复

本轮按实际网络角色配对：本机标签为 `client`、实际为 host；内网端标签为 `host`、实际为 client。MCP 双端只读观测持续 40 秒，并同时读取了当前会话诊断 `.log`、`.trace.log`。

加入方从 `SESSION_BEGIN` 到本地 P2 完成 `SetPlayerCharacter` 共约 16.711 秒，其中：

1. 等待本地 PID 从 `not-set` 变为 `set` 约 4.009 秒。
2. Workshop 地图加载约 2.681 秒，`SpawnJoinedPlayers` 在会话 `+7.557s` 出现。
3. `MonitorPlayerDropin` 从 `+7.986s` 开始运行，但输入对应的 `AddLocalPlayer(playernum=1, controllerID=0)` 直到 `+16.596s` 才出现，中间约 8.610 秒没有进入本地加入请求。
4. 一旦执行 `AddLocalPlayer`，本地 `AddPlayer` 用时约 61ms，英雄类型回复约 48ms，`SetPlayerCharacter` 在请求后约 115ms 完成；18 秒备用生成没有触发。
5. host 收到 `RequestJoinGame` 后约 2ms 即执行 `AddPlayer`，约 0.96 秒后完成远端 `SetPlayerCharacter`。延迟不在 host 槽位分配或英雄回复阶段。

现有追踪没有原始攻击键的准确时间戳，但源码确认 `MonitorPlayerDropin` 只有在场景进入原生玩家循环后才读取攻击键。加入房间后立即按下的输入可能发生在该循环就绪前，不能作为可靠的晚加入触发方式。

本轮实现调整：

- 晚加入检测完成后先加载 Workshop 地图，不再在加载前调用固定控制器 `AddLocalPlayer(-1, 1)`。
- 客户端配置场景和原生 `SpawnJoinedPlayers` 都就绪后等待 250ms，再使用 `Platform.GetPrimaryUserController()` 返回的本机主控制器自动发起一次 `AddLocalPlayer`；无法读取时回退到控制器 0。
- 已有本地槽位或已有待处理请求时直接复用；现有的跨控制器请求锁和 `SpawnJoinedPlayers` 重复空槽清理继续生效。
- 新增场景就绪、`SpawnJoinedPlayers`、自动请求和完成日志。

## test011 修复后验证与日志静默

修复后的双端只读观测持续 40 秒。加入方没有通过攻击键触发加入，日志确认新状态机按以下顺序执行：

1. `Late workshop client scene loaded` 出现在会话 `+10.056s`。
2. `Late workshop SpawnJoinedPlayers observed` 出现在 `+10.112s`。
3. 自动 `AddLocalPlayer(-1, controller=0)` 出现在 `+10.378s`，与设定的 250ms 稳定等待一致。
4. `AddPlayer`、英雄回复和 `SetPlayerCharacter` 在自动请求后约 65ms 内完成。
5. 观测结束前两端始终各保留一个本地角色和一个远程角色，没有重复角色或掉线。

同时发现原生 `MonitorPlayerDropin` 会在正常游玩输入期间继续扫描空闲的 P2/P3 槽位，导致保护层每几百毫秒记录两条 `Suppressed duplicate Workshop local-player request`。这些调用使用的控制器已经绑定到现有本地玩家，原生 `AddLocalPlayer` 本来也会将其忽略。

日志处理调整为：同一已激活控制器和同一待处理请求的重复调用直接静默；只有其它控制器尝试新增本地玩家时保留警告，并按控制器每 10 秒最多记录一次。玩家槽位保护行为不变。

## 主机迁移后原房主重新加入无法操作

本轮完成两次各 40 秒的双端 MCP 只读观测。原房主离开后，剩余端继续留在 `Test Evan2` 并保留自己的本地角色；原房主随后通过 `SteamLayer.JoinLobby` 以实际 client 身份重新进入原房间。

重新加入端的角色生成链完整成功：

```text
HeroController.AddPlayer
Player.Start(lives=1, IsMine=True)
HeroController.RequestHeroTypeFromMaster
HeroController.RecieveHeroTypeFromMaster
Player.SpawnHero
HeroController.SetPlayerCharacter
```

因此问题不是角色没有本地所有权、生命为 0 或英雄回复丢失。运行时状态同时显示重新加入端为 `ConfirmationPause`，后续出现 `MenuPause`，而留在房间的一端始终为 `UnPaused`。反编译源码确认：

1. 暂停确认框把 `PauseController.pauseStatus` 设置为 `ConfirmationPause`。
2. 原生 `PauseController.SetPause(UnPaused)` 只调用 `TogglePause`，而 `TogglePause` 不处理 `ConfirmationPause`，所以状态没有真正恢复。
3. `Player.GetInput` 在角色 `controllerNum` 等于 `PauseController.pausedByController` 时直接把所有输入设置为 `false`。

监控中还看到本地和远端角色都使用 `controllerNum=0`。这是不同机器各自主控制器的正常编号；原生 `GetPlayerNumForControllerID` 和 `GetPlayerUsingController` 都会结合 `PID.IsMine` 过滤，因此本轮不修改网络控制器编号。

本轮修复在新的有效 Workshop 线上会话开始时直接清除陈旧的 `pauseStatus` 和 `pausedByController`，并隐藏遗留的暂停相机和玩家列表。下一轮复测必须确认：

- 重新加入端日志出现 `Cleared stale pause state before Workshop online session`，其中旧状态为 `ConfirmationPause` 或 `MenuPause`，旧控制器为 `0` 或实际暂停控制器。
- 进入地图后 MCP 显示重新加入端为 `UnPaused`，本地角色仍是 `IsMine=True` 且可以立即移动、跳跃和开火。
- 角色槽位仍只有一个本地角色和一个远端角色，不因输入修复增加玩家或改写远端控制器编号。
- 两端继续单独记录 `GeneratePole.Awake` 异常；该地图对象错误不作为本次输入修复的通过或失败依据。

## 主机迁移输入修复验证

修复后的版本已完成实机验证。房主退出并发生主机迁移后，原房主重新加入之前的房间，角色能够正常生成并恢复移动、跳跃和开火；“角色存在但无法操作”的问题未再复现。该结果确认陈旧 `ConfirmationPause`/`pausedByController` 是本问题的直接原因。

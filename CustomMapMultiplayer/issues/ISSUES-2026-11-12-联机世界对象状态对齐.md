# 联机世界对象状态对齐

状态：本文记录早期世界对象状态同步改造；当前协议已演进至 13，补充燃烧时长、燃烧伤害、油污和油桶引爆计时。后续弹体、命中反馈、车辆爆炸和村民位置修复见本目录对应专项记录。本文保留早期根因与实施结果，不能据此认定所有对象类型均已验收。

## 后续补修：自爆兵、自定义命中视觉与惊吓

本次仅依据源码检查与离线补丁兼容性检查，不启动游戏或执行游戏内回归。

- `MookSuicide` 和 `MookSuicideUndead` 的无参 `MakeEffects` 包含爆炸、伤害与碎尸，先前未被弹体的六参同名入口覆盖；各端仍根据独立死亡计时和动作触发爆炸。现在拦截副本的独立触发，拥有端将实际爆炸标记纳入可靠终态，副本按权威坐标播放一次相应火焰／亡灵爆炸视觉，再沿原有碎尸与销毁状态清理。爆炸伤害复用目标拥有端转发，避免停用副本爆炸后远端英雄免伤；不在副本重新执行破土、点燃或二次爆炸伤害。
- Aquabro 的水爆已经通过原生长矛 `MakeEffects` RPC 发送，但新通用弹体前缀会拦截副本的该调用；基础 reverse patch 视觉也无法替代角色自己的水花。修正通用层：默认命中消息在原方法实际执行后发送，其他前缀完整接管时不产生基础命中消息；对具有外部前缀的原生命中消息校验对象 NID 和真正拥有端，允许其在禁止重复世界伤害的上下文中运行。无需改写 Aquabro 的水爆协议或角色生产代码。此处定位的是松开发射后的命中水爆路径，按住攻击时的角色蓄力动作仍需用户另行确认具体表现。
- Aquabro 鲨鱼的 `SkillSharkPanic` 只由技能拥有端调用目标 `Panic`。原生 AI 队列同步未包含维持受惊动作和头顶表现的 `blindTime`，原世界快照同样缺少该字段及 `scaredTime`。现在通用快照携带两项计时和心理状态，可靠传输进入／结束，副本按收到后的经过时间恢复。英雄在自身更新中触发远端对象的 Panic／Blind／Terrify 时，按目标身份请求其拥有端执行；同一通路覆盖加入方施放技能，不把副本 AI 重放当作新的惊吓请求。
- 协议升级为 5，双方须使用同一新版。离线使用实际部署的 Harmony 库检查默认命中、自定义前缀接管、异常后的上下文恢复，三项通过；该检查不运行 Broforce，不构成双端技能验收。
- Release 编译通过，已终止双端游戏并部署同一 DLL 与 Info.json，两端保持关闭。Aquabro 生产代码及角色 DLL 未修改。

用户下次手测：双方分别释放鲨鱼，比较同一敌人的受惊逃跑、头顶表现与结束恢复；普通与满蓄力三叉戟分别命中敌人、地形及自然到期，比较水花位置、大小和是否重复；普通／亡灵自爆兵分别主动自爆、枪杀后延迟自爆及连锁爆炸，比较消失、爆炸位置、双方玩家受伤和地形结果。游戏保持关闭。

## 本轮补修：近战、弹体、盾牌与周期性掉帧

用户要求修改后启动双端，由用户自行验证；本轮仅只读检查既有现场，不模拟输入、攻击或重开。

交付：Release 编译通过，已停止双端旧进程并部署相同 DLL/Info.json，双端重新启动且停留 MainMenu；只读确认弹体、盾牌和命中特效补丁已加载。未进行游戏内验收，保持游戏运行交用户手测。

- 现场盾兵 `183|0|100097|3`：本机 `hasShield=false`、health=3，加入方尚无丢盾盾兵。原状态模型确实未包含盾牌。协议 4 纳入装备标记，并在副本重放丢盾表现，禁止副本自行决定丢盾。
- 原生 `TestVanDammeAnim.Damage` 同时扣血并生成近战击中特效与血液；副本整段 Damage 被拦截后，这些瞬时视觉也丢失。现在用 transpiler 接住该方法中真正执行的视觉调用，可靠传输实际参数；不重新执行 Damage，不在晚加入时重播历史命中，也不依赖目标仍存在。
- 弹体原先本地推进、制导和寿命仍运行，收到 12Hz 状态时又直接重设位置和速度，形成互相覆盖。现在登记弹体的副本 Update/FixedUpdate 只显示权威轨迹及基础烟雾，位置与方向连续插值，丢包时最多外推一个发送间隔；Fire 的副本出生碰撞也不再独立结算。实际碰撞与基础弹体/火箭命中视觉单独发送。

- 移除周期性完整基线；首次加入、重入和权威代次变化仍获取完整状态。清理失效候选和瞬时弹体完整记录，静态状态仅发送变化，地形边缘仅在首次应用破坏状态时补齐，逐帧校正仅遍历单位列表。高频会话判断直接读取原生连接状态；被接管的副本同时拒收原生插值队列，避免保留不消费的状态。
- 已读取双端最新普通日志和 trace 日志；此前显示为 0 字节的最新文件也实际读取。此次后续读取已有内容，不再把历史的 0 字节状态当作当前状态。

验收待用户执行：关闭 TestMod 自动清敌后重新联机；双方分别用小刀击中普通敌人，观察击中闪光与血液；让盾兵丢盾，比较装备、材质和动作；让敌人连续射击并发射火箭，比较子弹连续性、导弹位置、方向及烟迹，并分别确认双方玩家仍可受伤、双方射击仍可伤敌和破坏地形。继续游玩数分钟，检查周期性严重掉帧是否消失，再覆盖退出重入和重开后的状态。

## 问题与结论

用户在当前联机现场发现狗的位置、状态和上方炮车方向不一致，并明确要求处理各种对象的对齐问题。此次检查确认范围已涉及普通敌人、大个子、狗、车辆和尸体的坐标、血量、动作或朝向。

当前快照中的网络对象身份全部对应，分歧发生在登记之后。原版混合同步依赖动作队列和各端本地模拟，持续状态、关键状态变化及晚加入恢复覆盖不完整；现有 Mod 主要补普通 Mook 的一次死亡和尸体终态，无法使整个世界持续收敛。不能继续以狗、炮车各加一个补丁作为整体修复。

源码能证明上述缺口存在；本轮没有记录每一次命中发生的全过程，不能把每个样本的首次分叉都归因于同一具体入口，也没有证明这是 Mod 单独引入的问题。

## 源码定位

源码入口为 [Broforce 源码分析](../../Broforce_src/Broforce-Source/!SOURCE_ANALYSIS.md)。该目录是反编译参考源码；实现应通过本 Mod 的 Harmony 补丁及现有 RPC 接入，不直接把该目录当完整 Unity 工程重建。

### 动作队列不能代替完整状态

[PolymorphicAI.cs](../../Broforce_src/Broforce-Source/PolymorphicAI.cs) 的 `Update`（约 288 行）主要限制拥有端 Think，但 `LateUpdate` / `RunQueue` 仍在各端执行。只有动作队列变化时才发送 `Sync`（约 816 行），持续很久的同一个动作不会定期提供完整校正。

`Sync`（约 837 行）不带 health、方向或形态。位置校正只在本地 Idle/Hanging、health>0 等条件下执行，通常误差大于 32 才修，且车辆、部分异形和特殊动作还有例外。远处的 `DisableWhenOffCamera` 又按各端本地视野停用 AI/单位，分叉可能长期冻结。

### 两条原生状态通路都不完整

| 通路 | 原生入口 | 实际覆盖与缺口 |
| --- | --- | --- |
| 连续状态 | [SyncController.cs](../../Broforce_src/Broforce-Source/SyncController.cs) `Update` / `SerializeAllOwnedObjects`，约 25 / 57 行 | 12Hz，仅发送 `ComponentsToSync` 中已开启同步且本端拥有的对象；字段来自 `[Syncronize]` 属性，不含通用 health/action |
| 完整状态 / 晚加入 | [NetworkObject.cs](../../Broforce_src/Broforce-Source/NetworkObject.cs) `GetState` / `PackState`，约 356 / 377 行 | 与连续属性是不同通路；基类 Pack/Unpack 为空。当前运行时 Tank、炮车及其武器继承的是空实现 |
| Mook 完整状态 | [TestVanDammeAnim.cs](../../Broforce_src/Broforce-Source/TestVanDammeAnim.cs) `PackState` / `UnpackState`，约 10408 行 | 包含 health/action/pilot，但不等于持续同步，也未补齐位置、方向、形态和完整生命周期恢复 |

[NetworkObject.SetSyncingInternal](../../Broforce_src/Broforce-Source/NetworkObject.cs)（约 405 行）只处理旧 `EnemyAI` 的启停，不处理 `PolymorphicAI`。而 `TestVanDammeAnim` 的移动、射击和局部模拟也不会因此全部停下。全对象调用 `EnableSyncing(true)` 既不能补齐字段，也不能保证副本停止结算，还会增加负载。

### 方向和形态需要按类型恢复

- [NetworkedUnit.DirectionSynced](../../Broforce_src/Broforce-Source/NetworkedUnit.cs)（约 97 行）更新 scale 和 `syncedDirection`，不会更新 [Tank.facingDirection](../../Broforce_src/Broforce-Source/Tank.cs)。炮车转身和发射都依赖后者，转向阶段又涉及 turnFrame、炮架展开与武器子对象。只改 scale 无法修好车辆。
- [MookDog.TransformIntoMegaDog](../../Broforce_src/Broforce-Source/MookDog.cs)（约 238 行）同时更新素材、碰撞、移动参数，并将 health/maxHealth 设为 15。恢复时应先应用必要的形态转换，再恢复权威血量；只设 bool 或最后重放转换都会出错。
- `MookArmouredGuy` 有自己的 pilot 和 PackState 路径；驾驶、寄生、复活等也必须保留关联，不能用普通 Mook 的字段赋值替代全部过程。

### 命中、伤害与死亡会放大分叉

[Map.HitUnits](../../Broforce_src/Broforce-Source/Map.cs)（约 1440 行）使用本端坐标和碰撞范围挑选目标，再由 `KnockAndDamageUnit`（约 2948 行）结合 [DamagePolicy](../../Broforce_src/Broforce-Source/DamagePolicy.cs) 决定本地伤害和网络伤害。运行时读取了策略资源：本地英雄打远端轻单位、英雄副本打本地轻单位，以及英雄打重单位的若干常规组合均为 AcceptDamage=true、NetworkDamage=false。不能假设每次命中都会额外发送一次扣血 RPC。

[Tank.Damage](../../Broforce_src/Broforce-Source/Tank.cs)（约 780 行）还按本端 `Time.time` 的 0.096 秒窗口限制伤害；事件落在不同帧可以得到不同扣血。`Unit.Death` / `DeathRPC`（约 399 / 418 行）只有位置和冲量，没有权威 hp、方向或生存周期版本；非英雄副本也可能先判死。车辆死亡包含燃烧、范围爆炸、移出单位表和武器死亡等副作用，重复调用 Death 校正会重复结算。

这意味着仅定期写回 health 也不足够：副本如果已经错误触发死亡、爆炸、掉落或地形破坏，恢复 hp 并不能撤回这些结果。

```mermaid
flowchart LR
    A[相同网络编号] --> B[两端各自执行动作与模拟]
    B --> C[位置或转向分叉]
    C --> D[各端命中和扣血不同]
    D --> E[死亡与爆炸结果不同]
    E --> F[地形和后续碰撞不同]
    F --> C
```

### 部分游戏弹体没有网络身份

[ProjectileController.SpawnProjectileLocally](../../Broforce_src/Broforce-Source/ProjectileController.cs)（约 124 行起）直接实例化并 Fire，没有稳定网络 NID。[MookArtilleryTruck](../../Broforce_src/Broforce-Source/MookArtilleryTruck.cs)（约 107 行）还在各端分别取随机值决定本地炮弹速度。同样的发射动作不保证同样的轨迹和命中。

[Projectile.Fire](../../Broforce_src/Broforce-Source/Projectile.cs)（约 36 行）已会执行出生点碰撞和伤害，之后 Update 又持续本地检测。只在生成完成之后拦伤害可能已经太晚；把副本 damage 改成 0 也会影响穿透和消失判断。普通 Grenade 同样不能只靠 XY 保证引信、爆炸和地形结果一致。

### 可靠传输与恢复仍有缺口

[Registry.RequestNetworkObjectSync](../../Broforce_src/Broforce-Source/Registry.cs)（约 534 行）是握手时的状态发送，不是周期修复；空 PackState 会被跳过。已有 destroyed map objects、dead/collapsed doodads 和 replacement blocks 应继续复用。

[NonStaticRPCObject.Execute](../../Broforce_src/Broforce-Source/NonStaticRPCObject.cs)（约 15 行）在目标尚未登记时直接返回，连续状态接收也会忽略缺对象。可靠传输不能保证尚未登记的对象最终应用成功。不能全局重试旧 RPC，因为伤害、爆炸等可能重复发生；新增协议需要自己的幂等应用和有限待登记队列。

### 改造前 Mod 死亡补丁的边界

原 `src/HarmonyDiagnostics.EntityFinalState.cs` 的资格检查（约 164 行）只覆盖有 PolymorphicAI 的普通非 Boss、非 Vehicle Mook，Tank 家族不在其中。该文件已由下述持续状态实现替换。

死亡只提交一次；尸体终态提交后移出候选，接收端同 sequence 且 TerminalApplied 时直接丢弃。终态仅含 NID、sequence、XY、health，没有方向，记录约 15 秒后清理，也没有完整晚加入重放。尸体被再次啃咬、炸飞或复活时，原来的“一次终态”不能代表新状态。应把这条路径并入可更新的生命周期状态，避免新旧两套同时写同一对象。

## 整体修复设计

### 1. 每种游戏结果只有一个结算方

场景敌人、机关和地形以实际场景拥有端为权威；`Owner=TargetServer` 应解析为当前 Host，不能和 Host 的数值 PID 直接等同。已有玩家拥有的动态对象继续按真实归属处理，玩家输入和角色控制保留本地响应。驾驶等所有权转移需要显式交接。

开火发起方和目标状态结算方可以不同：玩家端发送一次带编号的射击/近战请求，目标权威根据该次攻击结算世界结果，再提交唯一结果。玩家角色的受伤继续对接其拥有端，来自世界权威的命中事件应只应用一次。具体请求字段按武器需要选取，包含攻击起点、方向/初速度和必要随机结果，不能只转发一个待扣血数字。

副本可以预测移动、枪口和命中特效；在已接管的通路中，不能提前提交不可逆的敌人死亡、爆炸、掉落、消费或破坏。替换一个伤害入口时必须同步关闭该入口原来的重复结算路径，并清点近战、火/酸、碰撞、挤压、爆炸和连锁伤害；不能在原版本地扣血之外再叠一遍 RPC。延迟下的玩家射击与移动目标命中需要专门验收，不能以主机低延迟结果代替。

### 2. 统一身份、版本和状态消息

沿用完整 NID，并携带关卡代次、权威代次、生存周期和单调版本；同 NID 复活进入新生存周期，重开和 Host migration 进入对应新代次，旧消息不能覆盖新对象。SID 只有有限取值，不能单独当永久唯一关卡版本。

| 消息 | 内容与时机 | 应用要求 |
| --- | --- | --- |
| 运动快照 | 活动对象的逻辑 XY、速度、必要动作/转向阶段及权威时间；可用不可靠批量消息 | 按时间取新值并插值表现，丢一帧可由后续覆盖；不重放死亡或爆炸副作用 |
| 关键状态提交 | 生成、形态、命中结果、血量、死亡、复活、占用/领取、坍塌、销毁；可靠发送 | 按对象/事件版本幂等应用，同时保留可恢复的当前状态；死亡等转换一次生效 |
| 完整基线 | 当前对象状态、必要关系和已销毁/已消费记录 | 可从中恢复游戏语义，无需重演历史爆炸、奖励或伤害 |

运动时间序列和关键状态版本分开处理：旧运动包不能把新死亡/复活状态覆盖掉，新运动包也不表示此前可靠事件已应用。快照只写字段不能替代类型生命周期；补齐死亡状态时要修正碰撞、单位表、武器和动画，并抑制重复世界副作用。

新增消息使用现有 Steam/FRP 的 RPC 字节通路和稳定接收入口，在载荷中携带对象 NID。缺对象时只缓存本协议的有限幂等消息；登记后应用，遇销毁记录或旧代次则丢弃。超出等待/容量范围时请求对象基线，不能无限重放任意原生 RPC。

### 3. 按对象家族补全语义

| 家族 | 必须覆盖的状态与行为 |
| --- | --- |
| 普通敌人、狗、大个子及其它 TestVanDammeAnim 单位 | 位置、必要速度、方向、hp/maxHp、关键 action、形态与碰撞变化；死亡、受力、复活和持有/驾驶关系 |
| Tank、运输车、炮车、独立武器 | 逻辑 facingDirection、scale、转向/展开阶段、hp、死亡，以及车体与武器生命周期关联；驾驶时同步控制归属 |
| 游戏弹体与 Grenade | 唯一射击/生成事件、prefab、初始参数、随机结果、引信/寿命及命中/爆炸版本；决定穿透、消失和伤害的结果由权威提交 |
| 箱体、可移动方块、机关与陷阱 | 可碰撞位置、受损、坍塌/破坏、危险是否有效等游戏语义；复用原生地图破坏和替换记录 |
| 道具、奖励、救援和其它可交互对象 | 唯一消费/领取/救援结果、持有关系及后续生成物；保留现有已验证的拾取幂等路径并统一版本 |

没有 NID 的游戏弹体由权威为一次发射分配稳定事件编号；能使用原生已登记 prefab 清单的继续使用原生网络实例化，不能假定所有 prefab 都已进入清单。其余通过明确的生成事件和映射接入，不按坐标猜对象身份。纯视觉特效无需全部联网。

远端副本的 AI、动作执行、移动、碰撞和表现需要逐类接入，不能简单禁用整个 Update。炮车等子类在基类归属判断之外也有本地改队列逻辑，接管时必须同时处理。逻辑坐标与表现插值也要分清：只平滑 transform 却让碰撞继续使用另一套 X/Y 不能解决命中差异。

停用前提交最终游戏状态，重新进入活动范围前补一次基线。`enabled`、`activeSelf` 和可见性常由本端视野裁剪决定，不直接作为全网必须相等的字段。尸体稳定后可休眠，但再次受力、被吃或复活时必须重新标记变化；销毁/消费记录保留到该关卡生命周期结束。

### 4. 晚加入、重开和迁移使用同一状态模型

晚加入先完成原生生成及登记，再分批应用带版本的完整基线，并衔接基线期间产生的增量。单位形态先于血量恢复；驾驶和父子关联按依赖就绪应用；已销毁对象不能被迟到生成消息复活。

基线恢复不能把客户端冻结到整个世界复制完成才无限等待，应记录批次完成点和增量版本，缺少单个对象时请求该对象补发。重开清理上一代缓存、待应用消息和身份映射；主机迁移从已提交状态建立新权威代次，拒绝旧主机迟到消息。FRP 不支持的迁移不因此宣称支持。

### 5. 成本与接入范围

- 登记、生成、关键状态变化和交互时维护候选/变化集合，开关清理复用项目现有会话生命周期。
- 活动单位可先以原生 12Hz 作为评估起点，按类型、距离、字节预算分批；静止、休眠和静态地形按变化发送，并安排有预算的低频校正。频率是实现时调节值，不是已测得的性能结论。
- 不逐帧扫描此次 21,857 个网络组件，不对所有对象做反射字段快照，不持续可靠广播全地图。类型元数据和对象候选只在必要时更新，复用现有性能计数。
- 首个启用范围沿用明确的联机会话条件，避免遗留 Workshop 配置影响官方图。官方图同构建联机应单列验收；所有端必须支持新增状态协议，不能默认与未安装 Mod 的游戏兼容。

## 实施顺序与交付标准

1. **单位及车辆共用状态基线和生命周期。** 建立协议版本、登记缓存及类型适配，一次覆盖普通单位、Tank/车辆及关联武器；支持方向、形态、hp、死亡后再变化和同 NID 复活，合并现有尸体终态路径。此阶段可以证明状态恢复能力，不能据此宣布伤害和整个世界已经一致。
2. **弹体与伤害结算闭环。** 接入本地生成的游戏弹体、射击事件和目标权威结算，逐入口移除重复副作用；把车辆转向、发射、命中、爆炸和地形变化连起来验收。
3. **场景交互及恢复闭环。** 将可碰撞箱体、机关、陷阱、拾取与消费接入相同版本机制，完成晚加入、重开、迁移和遗漏对象补发。晚加入的单位基线从第一阶段实现，最后一阶段补齐全部已接管家族。

不复用已废弃的早期动态世界同步实验。特殊 Boss、复合单位和 Mod 新增类型需要逐类登记覆盖；发现未适配类型应明确列出，不能以继承了 Unit 就声称语义全部支持。最终覆盖清单和实测矩阵决定完成范围。

正式测试先关闭双端自动清敌并重开；先在当前 Workshop 地图复测，再覆盖其它对象组合。每项按完整 NID 或发射事件编号关联双端观察，不能只比较截图。

| 范围 | 场景 | 通过条件 |
| --- | --- | --- |
| 活动与休眠单位 | 狗、大个子、普通兵、盾兵；靠近、离屏、再返回 | 活动运动允许插值时差，停止后位置收敛；hp、形态、关键状态最终一致，无错误死亡/复活 |
| 车辆及武器 | 双向转身、展开、发射、受伤、驾驶、死亡 | 逻辑方向与表现对应；发射参数和命中结果一致；车体/武器生命周期无重复爆炸 |
| 多入口伤害 | Host/Client 分别开火、近战、爆炸、火/酸、碰撞和连锁伤害 | 每次权威结果只结算一次；无漏伤害、双倍伤害、重复掉落或地形破坏 |
| 尸体与复活 | 落稳后再炸飞、狗啃尸体、复活后再次死亡 | 后续变化继续传播；旧终态不覆盖新生存周期 |
| 箱体、机关与领取 | 下落、受损、破坏、陷阱触发、同时领取 | 比较有效碰撞、危险、消费和生成结果，不要求各端裁剪字段完全相等 |

| 关卡及所有权 | 重开、切关、Steam 主机迁移、驾驶交接 | 缓存清理正确，旧代次不污染新状态；迁移边界符合实际支持范围 |
| 网络和性能 | Steam/FRP，正常延迟及适度抖动/丢包 | 不可靠运动可恢复，可靠关键结果最终应用；无全图逐帧扫描或可靠消息积压 |

## 本轮结果

初始只读检查后，已按用户要求实施以下改造：

- 用 [HarmonyDiagnostics.WorldState.cs](../src/HarmonyDiagnostics.WorldState.cs) 替换原普通 Mook 一次死亡/尸体终态通路。登记非英雄 Unit、Doodad、Block、Projectile 和 Grenade，增加真实拥有端校验、关卡代次、状态版本、周期基线、待登记恢复及销毁记录；普通静态方块在变化时纳入。
- 持续同步位置、速度、血量、动作、方向及必要类型字段，包含狗变异、车辆转向与炮架状态；通过 LateUpdate 校正单位副本。副本伤害和生命周期重放增加结算限制，避免重复伤害和爆炸。
- 新增 [HarmonyDiagnostics.WorldProjectiles.cs](../src/HarmonyDiagnostics.WorldProjectiles.cs)，接管非英雄世界对象经 `SpawnProjectileLocally` 生成的敌方弹体，在 Fire 前分配网络身份，并发送拥有端确定的生成参数。

首版 Release 编译成功，`BUILD_INFO buildHash` 为 `698f28269c4867b19905bc693778301c4ed4cea91e109a675f6f6cc426cf0518`（源码及构建输入哈希，不是 DLL 文件哈希）。停止双端游戏后已复制同一 DLL 和 Info.json，随后双端启动成功。当时未执行部署后的伤害、场景对象或联机一致性验证，由用户自行手测。

上述实现不代表初始设计全部通过：加入方攻击能否经原生重放到达目标拥有端必须优先实测；特殊 Boss、复合单位、复活依赖和所有权迁移尚未逐类验收；普通 Grenade 沿用原生生成，未重写全部爆炸事件。不得将编译、部署和启动成功记为联机修复验收通过。

### 用户初测后的销毁漏接修正

- 用户反馈首版仍有不同步。双端当前运行的 `BUILD_INFO buildHash` 均为首版构建，状态协议的 epoch 相同，加入方已收到基线，因此此次不是未加载新版或协议未启用。
- 当前 SID 为 137：狗 `137|0|100144|3`、大个子 `137|0|100092|3` 在房主注册表中已无有效实例，加入方仍有有效实例。双方缓存中该狗的最后状态完全相同：revision=19574、health=1、Flags=None、位置约 `(892.54,2216)`；销毁没有进入后续状态。
- 原实现只补丁 `NetworkObject.OnDestroy`；原生 `Mook.OnDestroy` 不调用 base，部分其它对象也有独立实现。拥有端实际销毁后，候选因对象为 null 被跳过，基线仍保留旧存活状态，副本永久残留。
- 修正为同时补丁游戏程序集内各 BroforceObject 派生类声明的 OnDestroy；继承链调用 base 时复用已记录的 Removed 状态，避免重复提交。新增状态仍由实际拥有端发送，客户端生命周期重放继续抑制重复结算。
- 本次 Release 编译成功，已部署双端并启动游戏。用户再次明确要求后续不由代理进行游戏验证，因此本次部署后未执行联机或对象行为测试。该修正只针对已定位的销毁漏接，不将整体验收标为通过。手测优先覆盖狗、大个子、尸体清理，以及对象消失后加入方退出重入。

### 部分敌人死亡姿势不正确

用户随后补充部分敌人死亡后姿势不对。本次按用户要求只检查源码并修改，不读取或操作联机场景进行验证。

- 副本的 RunMovement 被拦截后，TestVanDammeAnim.CalculateGroundHeight 也不再执行；但 AnimateDeath 仍根据本端 groundHeight 选择空中或落地帧。Mook.AnimateDeath 还有翻滚、前后空翻、暗杀和电击等分支，首版快照未携带最终画面帧。
- 首版根据本端 actionState 是否为 Dead 决定要不要初始化死亡，而原生 PolymorphicAI.Sync 也可以先写入该状态，导致后续生命周期初始化被跳过。
- 协议升级为 2，为有主精灵的 TestVanDammeAnim 尸体追加拥有端的实际画面帧、SpriteSM 偏移、frame、groundHeight、冲量及纵向缩放；沿用已有旋转和朝向。姿势变化继续进入运动快照和完整基线，静止尸体不会仅因 frame 计数递增而持续发送。
- 副本已有尸体姿势时，由 ChangeFrame 前缀直接应用该姿势，LateUpdate 再恢复必要状态；初始化死亡与复活期间仍允许原生帧更新。死亡初始化按 Life/DeathLife 执行，避免被原生提前写入的 Dead 状态跳过。
- 本项 Release 编译成功，停止双端游戏后已部署同一 DLL 和 Info.json，双端启动工具均返回启动成功。按用户要求未执行游戏内验证，仍待用户验收：普通枪杀、近战、爆炸抛起后落地、落稳后再次炸飞，以及加入方退出重入后的尸体姿势。未宣称特殊材质、所有复合单位和全部死亡表现已经通过。

### 角色脚下地形边缘分歧

- 用户继续指出双端角色脚下方块不同。本次只读该现有现场定位，未操作角色、攻击或重开地图。SID 为 144，玩家约在 `(976.91,2344)`；脚下 `144|0|36287|0`、格子 `(61,146)` 为 DirtBlock，双方 health=5、destroyed=false、碰撞启用且地图占用相同。房主有顶部、左右边缘子物体，加入方缺失这些子物体。根 Renderer 关闭是由子方块显示的正常情况，不作为破坏判据；装饰贴块的随机变体差异也不作为碰撞分歧证据。
- 原生拥有端 `ActuallyCollapse(...,true)` 会通知四邻显示新露出的边缘；原生发往其它端的调用及本协议补状态均使用 `false`。接管副本本地伤害后，副本不再提前执行本地破坏，这条原先依赖本地破坏更新边缘的路径被漏掉。
- 为副本 `DestroyBlockInternal` 回调和权威破坏状态恢复补上四邻存活前景块的 Show*Edge 调用。已被原生 RPC 破坏的块收到基线时也会补边缘；不调用带 DisturbNetworked 等副作用的完整邻接坍塌方法。只处理当前前景格子对应的方块，避免背景块破坏错误露出前景边缘，并跳过已破坏邻块，避免重复创建背景碎块。
- Release 编译成功；终止双端游戏并确认本机进程退出、远端连接随自身进程终止断开后，已复制同一 DLL 和 Info.json，双端启动工具均返回启动成功。部署后未执行游戏内验证。验收仍由用户执行：分别由房主与加入方打掉支撑块的上、左、右邻块；比较两端支撑块是否保留以及新露出的边缘；随后退出重入检查边缘恢复。当前证据只确认显示边缘分歧，不将其它地形物理、随机装饰或整套世界对象同步标为已通过。

### 房主打碎尸体不同步，以及狗停在尸体旁不攻击

- 用户反馈房主继续破坏敌人尸体时，另一端没有同步破碎。源码确认：副本的 `Gib` 被统一变更前缀拦截，原生 `GibRPC` 因此无法生效；原有 Removed 状态只移除物体，没有携带碎尸原因或播放碎尸效果。只同步血量、死亡姿势或最终销毁均不能补齐这一转换。
- 协议升级为 3，在拥有端实际进入 `CreateGibEffects` 时记录碎尸类型和冲量，随可靠 Removed 状态发送，并保存在关卡销毁记录中。副本在移除前播放一次基础碎尸效果，同时从 `Map.units` 移除；重复状态由 destroyed 和销毁记录防止再次播放。基础视觉方法通过 Harmony reverse patch 调用，不执行会投放手雷、生成敌人或再次造成爆炸伤害的派生类覆写。碎片随机轨迹仍属于本地视觉，不承诺逐片轨迹一致。
- 用户还指出一只狗看见玩家但不攻击。只读当前现场：活狗 `12|0|100144|3` 位于约 `(840.2045,2184)`，双方 health=1、Idle、AI=Attracted；拥有端追逐尸体 `12|0|100142|3`，尸体位置约 `(830,2184)`。活狗列为 53，尸体列为 52；拥有端 AI 的 blockOffset=2.75，移动目标 X=834.75，距离 5.4545 小于 HalfWidth=6，因此移动队列判定到达，但 `DoAttractedThink` 仍要求处于尸体所在格子才进食，造成空队列与移动动作反复循环。此行为不能用强制切成 Alerted 代替修复。
- 为 DogAI 的尸体追逐移动补上与后续进食相同的格子到达条件，只约束拥有端正在追尸体的 Move，不改正常寻敌与攻击优先级。同一现场还确认加入方活狗 groundHeight=0、IsOnGround=false，而拥有端为 2184、true；禁用副本 RunMovement 后原本的地面高度计算被跳过。协议 3 将地面高度从尸体专有字段扩展到全部 TestVanDammeAnim 状态，并在接收和 LateUpdate 恢复，避免副本扑咬和其它依赖落地的动作被错误阻止。
- 上述逻辑不依赖地图、坐标或指定 NID。Release 编译通过；停止双端游戏、本机确认无游戏进程且远端进程自终止后连接断开，已复制同一 DLL 和 Info.json，双端启动工具均返回成功。按用户要求未执行部署后的游戏内回归，交用户验收：枪杀后继续打碎尸体、爆炸直接碎尸、狗进食后尸体破碎、无尸体时狗的追击扑咬，以及加入方退出重入后已破碎尸体不再出现。特殊单位的额外爆炸、掉落和全部伤害闭环仍未逐项验收。

### 本次补充：爆炸导弹表现、子弹特效与运动卡顿

- 用户继续反馈：当前角色附近发射爆炸导弹的 Mook 在双端的爆炸特效存在分歧；加入方子弹特效存在分歧，子弹运动持续一卡一卡。
- 原版依据：`MookBazooka.FireWeapon` 通过 `ProjectileController.SpawnProjectileOverNetwork` 发射弹体；`RocketSeeking` 继承 `Rocket.MakeEffects`，`BulletMook` 和 `MookMiniGunBullet` 继承 `Projectile.MakeEffects`。`ProjectileController` 的网络发射会向各端实例化弹体并 RPC `Fire`、随机种子和追踪目标。
- 特效漏发依据：`WorldProjectileEffectsPostfix` 原先用运行时类型的 `GetMethod("MakeEffects")` 与 Harmony 当前补丁方法做 `MethodInfo.Equals`。继承方法的反射结果带有子类的 `ReflectedType`；实际游戏运行库中 `BulletMook` 对 `Projectile.MakeEffects`、`RocketSeeking` 对 `Rocket.MakeEffects` 的相等比较均为 false，导致拥有端没有发送这两类特效 RPC。现改为沿继承链查找 `DeclaredOnly` 的实际声明，再与当前补丁方法比较；覆写中调用 base 时只由最外层覆写发送，`__runOriginal == false` 的自定义前缀仍继续拥有自己的特效和传输。
- 爆炸视觉依据：原版 `Rocket.MakeEffects` 在 `IsMine` 分支执行地形、单位、Doodad 与其它弹体结算，同时调用 `Map.ShakeTrees` 和 `EffectsController.CreateExplosionRangePop`。副本通过 reverse patch 调用该方法时 `IsMine` 为 false；为避免重复结算，伤害仍仅由拥有端执行，但之前也漏掉了树木/草丛摇动和爆炸范围环。本次在接收 Rocket 特效 RPC 时单独补播这两项视觉表现；`Rocket.MakeEffects` 的其余本地表现仍由原 reverse patch 播放。
- 运动依据：世界对象快照按约 12Hz 发送；旧 `WorldProjectileUpdatePrefix` 按接收时间将位置插值到最新快照约 83ms，再仅外推最多约 83ms 后停止。`ApplyWorldObjectState` 每次接包都重新设置插值起点，且包内没有拥有端采样时间。协议升至 6，为状态加入采样时间；加入方按拥有端时间保留最近 6 个弹体样本，延迟一个发送间隔插值，在缓冲末端之后沿最新速度外推。新 world epoch 会清理旧弹体时间轴；副本仍不运行碰撞或追踪 AI。尚未采集实际到包间隔，因此实机仍需确认是否还存在其它抖动来源。
- 本项不依赖指定地图、坐标或网络对象 ID；伤害、地形破坏和命中结算仍由弹体拥有端负责。Release 构建成功，`BUILD_INFO buildHash` 为 `6ead869c5ae751b9d17dd0c85984dfa753b1656c0d660a27bdfa047b26a52da7`，DLL SHA-256 为 `A64961577B45EBD95D6AACC6B7F6DA2CDC77E5C2729DE3AE06C4C8A9ABC26FC9`。标准部署脚本在远端 WMI 查询处遇到 Access denied 并停止复制；确认本机进程已退出、remote Inspector 停止远端成功后，将同一构建 DLL 和 `Info.json` 部署到双端，两个目标文件哈希一致。游戏保持关闭，未执行游戏内验收。
- 待用户实测：近距离 Mook 的 `RocketSeeking` 爆炸范围环和周边树/草丛表现是否双端一致；`BulletMook`、`MookMiniGunBullet` 等继承 `Projectile.MakeEffects` 的子弹特效是否到达加入方；加入方连续观察子弹飞行、转向、命中与寿命结束时是否仍卡顿，并确认伤害和地形结果只结算一次。当前没有实测网络到包间隔，编译和部署不代表这些联机行为已通过。

### 启动后双方显示死亡、角色未能出生

- 用户自行启动后反馈角色死亡。只读现场确认双方均在地图内，两个玩家槽位各有 1 条生命，但 `heroType=None`、`character=null`，出生追踪仍为 `firstDeployment=True`。本次是角色实例化中断，没有证据表明角色先出生再被伤害杀死。
- 日志明确记录 `PatchWorldHeroStatusContext -> WorldRegisterPostfix -> Registry.RegisterObject -> Player.InstantiateHero` 抛出 Harmony 的 `You can only patch implemented methods/constructors. Patch the declared method ... TestVanDammeAnim::LateUpdate() instead`。新增的英雄状态来源补丁通过子类反射取得继承方法，`ReflectedType` 与 `DeclaringType` 不同，导致登记阶段失败，并引发未初始化角色的后续空引用。

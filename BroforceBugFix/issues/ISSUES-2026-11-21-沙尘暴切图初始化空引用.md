# 沙尘暴切图初始化空引用

本记录保存 2026-11-21 的构建与实机验收结果；下文“未提交或推送”描述验收当轮结束时的状态。当前安装版本见[项目说明](../readme.md)，交付状态以 Git 记录为准。

## 结论与修复边界

原版 `GameModeController.LoadSceneCore` 先把 `Map.MapData` 设为 `null`，新地图稍后才由 `Map` 创建。场景交接期间，尚未初始化的 `Effects.Sandstorm.Update` 可能继续运行；它先写 `_hasSetup=true`，再调用未检查地图数据的 `Map.HasSandStormTrigger`，因此抛空引用并留下部分初始化状态。

`0.5.0` 的 `SandstormSetupFix` 仅在非编辑模式、尚未初始化且 `MapData` 为空时跳过这一帧的 Update，保留 `_hasSetup=false`。数据就绪后执行完整原版初始化；已初始化实例、编辑模式、有无风暴触发器、风力、方向、音效和协程均沿用原逻辑。不修改 RPC、关卡加载或网络流。

不能让 `HasSandStormTrigger` 在地图暂缺时直接返回 `false`：原版会据此标记初始化完成并永久关闭对象，可能把正常风暴一起关闭。本修复也不吞异常，不处理坏地图的空 TriggerList、空 trigger、空 actions 或空 action。

独立设置为 `EnableSandstormSetupFix`，默认开启；Harmony ID 为 `GJKen.BroforceBugFix.SandstormSetup`。UMM、主开关及独立开关必须同时开启。删除条件：上游在提交初始化状态前等待 MapData 就绪。

## 联机影响

这不是仅限离线的代码，房主和加入端都可能经过上述场景交接。异常会中断当前端这一帧的初始化；若故障对象继续存活，`_hasSetup=true` 会阻止重试，后续风暴启动可能因缺失音源再次报错。沙尘暴还影响风场、敌人避难及致命风暴判定，因此不能归为纯视觉问题。

历史出错的加入仍能完成入图和重开，双端各见两名存活玩家；没有证据表明这条异常本身损坏 RPC 流或必然导致断线。历史失败对象是否随旧场景立即销毁无法追溯确认，不能认定那次已经造成风暴不同步。

补丁在各端本地生效，不增加同步协议；建议联机双方都安装，以保护各自的场景生命周期。两端分别调用风暴 API 的受控检查只验证本地正常行为，不等同于完整风暴关卡的网络同步验收。

### 结尾超时的核实与无效试次

早期辅助路线在结束区域后出现 MCP 主线程任务超时，曾被暂时怀疑为游戏卡死。补读日志可见角色坠落导致 `LevelFinish(Fail)`，同时原版仍加载 `CutsceneAirFlex` 并记录网络更新。源码确认 `CutsceneController.LoadCutSceneRoutine → PauseController.SetIntermissionPause(true) → PauseGameObjects` 会停用所有未标记 `Unpausable` 的活动对象；Inspector 的 `MainThreadDispatcher` 默认也是 `Untagged`，因此过场期间无法处理 MCP 请求。超时不等于游戏主线程卡死，也不能据此把结尾问题归因于沙尘暴修复。

最终仅临时将 Inspector 调度对象标记为 `Unpausable`，不改原版暂停、过场、触发器或网络逻辑。修正辅助定位后两端角色均存活，能够直接读到 `CutscenePause`、完成普通确认输入并共同进入 `Polaroid`，结束后恢复调度对象原 tag。早期出现资源加载异常、以及两端互相移除玩家后未同步切图的试次均排除，不记为有效风暴或通关验证；关闭补丁时再次观察到的 `Map.HasSandStormTrigger` 空引用也不计为开启修复后的失败。

# ISSUES-2026-08-26 FRP 多客户端与地图内动态房间人数上限

## 状态

**已完成代码和部署；房主加两台加入方的三机基础联机已通过用户实测，四机与动态容量边界尚待验证。**

本文记录 FRP Direct 从单一加入方扩展到最多三台远端机器，以及房主在地图内动态设置 `1` 至 `4` 人房间角色上限的修改。用户已确认房主加两台加入方的三机基础联机正常；该结果证明两台 Client 能同时连接和游玩，但不自动证明四机、每个容量档位或地图内降额重入均已验收。

## 用户目标

房主通过 UMM 的 `FRP Direct` 面板点击固定的 `1`、`2`、`3`、`4` 按钮设置整个房间的角色上限，不需要输入数字：

| 按钮 | 房间角色上限 | 最多加入方 |
| --- | --- | --- |
| `1` | 仅房主 | 0 |
| `2` | 房主加一名加入方 | 1 |
| `3` | 房主加两名加入方 | 2 |
| `4` | 房主加三名加入方 | 3 |

该功能不突破 Broforce 原生四人限制。人数按钮只在 `FRP Direct role: Host` 时显示，Client 不单独设置容量，以房主发布的房间信息为准。

## 预期的地图内动态行为

房主进入地图后仍可打开 UMM 并点击人数按钮。人数变化应满足：

- 点击后立即保存并生效，不重启 FRP 传输，不结束当前房间。
- 降低上限时不踢出、不注销已经在房间里的玩家，也不删除现有机器或 PID。
- 新的加入请求立即按新上限判断。
- 当前人数超过新上限时，已经在场的成员继续游戏；成员退出后不能重新加入，直到房主再次调高上限。
- 提高上限后立即重新开放相应空位。
- 房主把最新 `capacity` 推送给 Client，Client 更新本机房间信息。

例如当前有三人，房主将上限从 `3` 改为 `1`，三人应继续留在地图中。任一加入方退出后，其重入应被拒绝；房主将上限重新调为 `3` 或 `4` 后，该空位应重新开放。

人数按钮继续与连接参数重启分离。FRP 设置现使用单一总开关并保留明确的 Host/Client 角色按钮；切换角色时只激活对应角色的端口或服务端地址。角色和总开关立即应用，端口、服务端地址及密码在停止输入后自动保存和重启，不再提供手动 Apply 按钮。人数变化仍在地图内立即生效且不会重启传输。

用户已完成本轮设置界面实测，确认单一总开关、Host/Client 切换和自动应用行为正常，不再需要额外开关或 Apply 按钮。

## 本轮实现

### 设置与界面

- `src/DiagnosticSettings.cs` 新增持久化字段 `FrpDirectPlayerLimit`，默认值为 `4`。
- 设置版本升至 `7`；旧设置只有在原传输开关与游戏层开关都开启时才迁移为新的 FRP 总开关，避免升级后意外启用。旧设置缺少人数或值不在 `1..4` 时仍迁移为 `4`。
- `src/Plugin.cs` 使用 `GUILayout.Toolbar` 显示四个固定按钮，不提供文本或数字输入框。
- 设置页只显示一个 FRP 总开关和一个 Host/Client 角色按钮；非当前角色的连接配置保留但不参与连接。连接参数自动保存和应用，不再显示 Apply 按钮。
- 人数发生变化时立即保存设置，并通过运行中的 `DiagnosticsBehaviour` 通知 FRP 传输层。
- `umm-settings-preview.html` 已同步四段按钮和“立即生效”提示。

### 多客户端传输

- `src/FrpDirectTransport.cs` 当前协议版本为 v4，Host 最多保持三台已认证远端连接。多客户端功能首次实现时使用 v3；后续为同步房主 RTT 快照升级到 v4，旧协议构建会因版本不匹配而拒绝连接。
- 每条远端连接独立维护握手、心跳、超时和机器 ID。
- 支持按机器 ID 定向游戏数据、广播、成员离开通知和重复机器 ID 拒绝。
- Client 到 Client 的游戏数据由 Host 中继。
- `PlayerLimit` 不再属于需要重启的连接配置键；人数变化通过 `PlayerLimitChanged` 事件即时发布。
- 底层认证连接上限仍为三台，不随房间容量降到零。这样满房客户端仍可完成认证和查询房间信息；实际加入由房间层判断。

### 房间与成员

- `src/FrpDirectLayer.cs` 按机器维护远端 `IDWrapper`、PID 和已加入成员集合。
- Host 的远端成员上限动态计算为 `PlayerLimit - 1`。
- 达到上限后的新加入请求返回 `room_full`。
- 单个 Client 离开只清理该机器的 PID，并通知其他 Client，不重置整个房间。
- 房主创建房间时将所选上限写入 `Connect.PlayerLimit`，由原生 `RoomInfo.RefreshInfo()` 写入 `capacity`。
- 地图内调整人数时刷新并发布当前房间信息，但不修改已加入成员集合。
- Client 在加入成功及收到房间状态更新时读取并钳制房主发布的 `Capacity`。
- 离开 FRP 房间后恢复 `Connect.PlayerLimit = 4`，避免影响后续原生 Steam 联机。

## 尚未验证的范围

以下项目均为**未验证**：

1. `1` 人房能否正确显示满房，并阻止所有加入方进入。
2. `2` 人房能否允许第一名加入方，并拒绝第二名加入方。
3. `3` 人房能否允许两名加入方，并拒绝第三名加入方。
4. `4` 人房能否允许三名加入方同时完成 PID 分配、角色生成、移动、攻击和 RPC 同步；当前只验证到房主加两名加入方。
5. 地图内提高上限后，新空位能否立即被另一台机器使用。
6. 地图内降低上限后，现有玩家能否继续操作且不会掉线、丢失 PID 或角色。
7. 当前人数高于新上限时，退出的成员能否被拒绝重入；重新调高上限后能否成功重入。
8. 所有 Client 是否都能收到更新后的 `capacity` 和玩家人数。
9. 三机基础游玩已证明常规 Host 中继可用；多 Client 成员退出、定向边界和异常断网仍需专项验证。
10. 多地图、切关、失败重开、高延迟、长期多轮退出/重入和主机退出场景。

当前仍不支持主机迁移。已通过的三机基础联机不能替代上述四机、各容量档位及动态调整测试。

## 建议验收顺序

### 容量静态测试

每个档位都应在创建房间前设置一次，并使用新的诊断会话 ID：

1. 房主选择 `1`，创建房间；远端查询房间并确认无法加入。
2. 房主选择 `2`；第一名加入方成功进入，第二名加入方被拒绝。
3. 房主选择 `3`；两名加入方成功进入，第三名加入方被拒绝。
4. 房主选择 `4`；三名加入方均成功进入地图并各自控制独立角色。

### 地图内动态测试

以三人已经进入同一地图为起点：

1. 房主从 `3` 改为 `1`，确认三人仍在线且可操作。
2. 一名加入方退出并立即重入，确认重入失败。
3. 房主改回 `3`，确认该加入方可以重新加入并恢复独立角色。
4. 房主依次切换 `2`、`4`，确认连接没有重启，现有玩家没有收到离开通知。
5. 完成一次切关或失败重开，确认最新容量仍有效。

### 证据要求

每轮必须收集所有实际参与端的诊断 `.log`、`.trace.log`、UMM `Core\Log.txt` 和游戏 `error.log`，并对齐：

- `BUILD_INFO` 与双方或多方 `buildHash`。
- `FRP_DIRECT room player limit changed without restarting transport`。
- `FRP_DIRECT active room player limit updated`，其中应包含 `currentMembers` 和 `existingMembersRetained=true`。
- Host 的加入接受或 `room_full` 拒绝。
- 每台机器的 PID 分配、`Player.Start`、`SetPlayerCharacter`、退出和重入事件。
- 调整人数前后的连接状态、房间 `capacity`、玩家数量和角色可操作性。

只有相应档位和动态流程按上述步骤形成多端证据后，才能把对应项目从“尚未验证”改为“已验证”。

# 2026-08-20 角色退出重入后无法操作问题记录

## 问题目标与分析范围

玩家遇到的核心问题是：角色退出 Workshop 线上房间后再次进入，虽然角色可能已经生成，但无法移动、跳跃或攻击；后加入房间的角色也曾出现相同现象。一次多轮 Workshop 线上测试后，用户反馈该问题暂时没有再次复现。本记录依据当时收集的诊断日志、两端 UMM 日志和本机游戏崩溃日志整理，没有在本次整理中启动 MCP；MCP 监控仍遵循文档中只有收到明确“开始”指令后才能启动的约束。

## 已确认正常

该次历史测试收集的晚加入日志显示：

```text
Reusing the last known local Workshop controller ... controller=1
Late workshop join requested a local player slot ... controller=1
Late workshop automatic join confirmed by local Player.Start ... controller=1
```

随后本地玩家均完成以下链路：

```text
Player.Start
RequestHeroTypeFromMaster
RecieveHeroTypeFromMaster
SpawnHero
SetPlayerCharacter
```

本地玩家的 `IsMine=True`、`controllerNum=1` 与实际输入控制器一致。日志中没有发现角色被设置为 `unknown` 或空角色；`Player.Start` 早期出现的 `character=null` 是英雄生成前的正常中间状态，后续都完成了 `SetPlayerCharacter`。

掉线重建时也能看到保存和恢复控制器、英雄类型的日志。例如：

```text
Saved local Workshop controller for dropout rejoin
Reusing saved local Workshop controller for dropout rejoin
Restored saved Workshop hero type during dropout rejoin
```

因此，当前不建议继续修改已经验证有效的角色控制器绑定路径。

## 相关现象：掉线重建后自动换人

此前一次双端固定 40 秒 MCP 监控确认：掉线后本地玩家槽位可以重新建立，`Player.Start`、`RequestHeroTypeFromMaster`、英雄回复、`SpawnHero` 和 `SetPlayerCharacter` 链完整执行；问题不是玩家槽位没有重建。

监控中，掉线前本机槽位生成的是 `DirtyHarry`。掉线后同一槽位重新请求英雄时，主机日志显示 `preferedNextHero=None`，随后本机收到并生成了 `Brominator`。远程端也观察到相同的原生重新分配路径。角色因此可能表现为短时间无法操作，随后被自动重建成另一个英雄。

该现象与控制器绑定问题相关，但根因不同：控制器绑定决定输入是否到达本地角色，英雄类型保存决定重建后是否还是玩家原来的角色。

### 英雄类型恢复修复

- 在 Workshop 线上会话中记录每个玩家槽位最近一次成功绑定的英雄类型。
- `Dropout`/`DropoutRPC` 发生时保存该槽位的原英雄类型。
- 主机处理 `RequestHeroTypeFromMasterRPC`、客户端接收 `RecieveHeroTypeFromMaster` 以及 `Player.SpawnHero` 时优先使用保存的类型。
- 18 秒本地备用生成也优先使用保存的英雄类型。
- 正常死亡换人和未发生掉线的普通英雄请求仍使用原生选择逻辑。

相关验证日志包括：

```text
Saved Workshop hero type for dropout rejoin
Restored saved Workshop hero type during dropout rejoin
```

重建时还应确认 `heroType`、`character` 类型与掉线前一致，并继续确认 `pauseStatus=UnPaused`、`pausedByController=-1`、`InputReader.IsBlocked=false` 和本地 `controllerNum` 有效。

## 仍存在的问题

### 1. Workshop 地图对象持续抛出空引用

该次历史测试收集的 `test011` 事件日志中，多数地图加载过程出现：

```text
NullReferenceException
GeneratePole.Awake()
Map.PlaceDoodad
Map.LoadArea
Map.SetupBlocksCoroutine
Map.Awake
```

该异常发生在 `Test Evan2` 地图加载期间。异常之后角色通常仍能生成并操作，但它可能影响地图中的杆子、碰撞体或出生点，不能再简单视为完全无影响。该问题仍与角色控制器修复分开记录。

### 2. 英雄回复中的玩家编号仍然异常

该次历史测试记录过以下警告：

```text
Normalized malformed Workshop hero response player number: received=43; using local pending player=1
Normalized malformed Workshop hero response player number: received=14; using local pending player=0
Normalized malformed Workshop hero response player number: received=38; using local pending player=0
Normalized malformed Workshop hero response player number: received=23; using local pending player=0
Normalized malformed Workshop hero response player number: received=12; using local pending player=0
```

玩家编号有效范围应为 `0-3`。当时的 Mod 可以使用本地待处理玩家槽位修正这些回复，后续英雄仍能正常生成，因此该次测试没有造成无法操作。但这说明原生网络回复或参数解析仍存在时序/协议异常；在不同的加入顺序下仍可能导致错误英雄或未知角色。

### 3. 长时间重复重入仍有超时

该次历史测试的两轮长时间重复重入过程中出现：

```text
Late workshop join timed out before the automatic local player join completed
```

对应时间约为会话开始后的 `147.146s` 和 `148.309s`。这些会话在此前多次重建成功，但最后一次重建没有在超时前完成，说明当时的长时间重复掉线重建还不是百分之百稳定。后续测试应使用新的会话 ID 重新确认。

### 4. 仍有重复本地加入请求

该次测试的部分会话出现：

```text
Suppressed additional Workshop local-player request because a local slot is already active: player=2; controller=1
```

保护层正确阻止了重复请求，没有生成额外角色；这不是该次测试中角色无法操作的直接证据，但说明原生 `MonitorPlayerDropin` 仍会扫描并触发已经占用控制器的空槽位。相关日志已经限频，暂不应通过放宽加入逻辑来处理。

## 本机原生崩溃

该次历史测试曾记录一份本机游戏原生崩溃报告（崩溃时间为 `2026-08-20 03:07:22`）。

报告内容为：

```text
Access Violation (0xc0000005)
Write to location 00000000 caused an access violation
Error occurred at 2026-08-20_030722
```

该时间与同一历史会话中的 `GeneratePole.Awake` 空引用发生在同一秒。该会话随后完成了角色生成，并在约 20 秒时执行 Workshop `Esc` 返回大厅。由于崩溃报告没有提供可解析的托管调用栈，目前只能确认时间相关，不能单独证明地图异常就是原生崩溃原因。后续是否仍有崩溃，必须以新测试产生的崩溃报告为准。

## 环境核对

当时本机和内网测试端的 UMM `Core\Log.txt` 均显示：

```text
SUCCESSFUL LOADED 5/5 MODS
```

两端均加载 `BroforceOnlineDiagnostics 0.4.0` 和 `Unity Inspector Mod`。项目安装包、本机 UMM 和内网部署目录中的 DLL SHA-256 一致：

```text
596381DA31CE6667203AFB9965F57F66AE71D9A710444E0703900A0285B2632E
```

当时通过共享路径读取到了内网端 UMM 日志，但内网端自己的 `Application.persistentDataPath` 诊断目录无法通过当前权限读取。因此当时对角色控制的判断主要依据是本机 `.log`/`.trace.log` 和双方 UMM 加载结果。若后续重新分析网络根因，应在日志清理前同时收集两端新会话的诊断日志、trace 日志、UMM `Core\Log.txt` 和游戏崩溃日志。

## 后续排查重点

1. 优先定位 `GeneratePole.Awake` 所需的地图对象或 `DoodadInfo` 数据，单独验证修复后是否仍会触发原生崩溃。
2. 保留英雄回复的原始参数和本地槽位映射，继续确认非法 `playerNum` 是否只发生在晚加入/掉线重建路径。
3. 对长时间重复掉线重建继续测试，重点观察超时前是否出现 `AddLocalPlayer`、`Player.Start` 或控制器占用状态缺失。
4. 角色控制器绑定修复在该次历史测试中表现正常，除非再次出现 `controllerNum` 与实际输入不一致，否则不要扩大该部分修改范围。

后续复测应使用新的会话 ID，并在日志清理前记录测试结果和关键状态。
